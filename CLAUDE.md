# Mouse — Multiplayer Whiteboard Platformer

## Concept

A browser-based multiplayer game best described as **a whiteboard app meets Transformice**: players share a canvas where anyone can draw platforms in real time, and everyone's mouse avatars can physically jump and run on whatever gets drawn. The world is shaped by its players as they play.

## Stack

* **Client:** HTML5 Canvas + Matter.js
* **Networking:** PartyKit (`partysocket` client, `Party.Server` server class) — runs on Cloudflare's edge
* **Physics authority:** Server-authoritative — the PartyKit room runs Matter.js; clients send inputs and render state snapshots
* **Language:** TypeScript throughout (the eventual PartyKit project; the early prototype is plain JS/HTML for speed)
* **Deployment:** PartyKit managed platform (server) + Cloudflare Workers Static Assets (client)

## Conventions established so far

* **Drawn paths are raw `{x, y}` point arrays.** Physics platform bodies are generated *deterministically* from those arrays (currently: a chain of thin rectangle segments, one per consecutive point pair — robust against arbitrary squiggly/looping/zigzag freehand shapes, unlike `Matter.Bodies.fromVertices` which mishandles concave hulls).
* **Render from the point array, not from body geometry.** Pixel art is purely cosmetic — physics fidelity comes from the shared point array. This separation is established in the prototype's custom `requestAnimationFrame` render loop (deliberately *not* using `Matter.Render`, the debug renderer) and must carry through to the real multiplayer client, where rendering is driven by synced point arrays rather than physics internals.
* **Ramer–Douglas–Peucker simplification is deferred.** It's a network-bandwidth optimization for the drawing-sync phase (step 6), not something the single-player prototype needs — raw points give more stable collision geometry when there's no transmission cost.
* **Local-player prediction is a deliberate, *scoped* exception to "the client does no local physics or prediction" — not a reversal of it.** [server/src/client.ts](server/src/client.ts)'s `predictLocalX` predicts only the *local* avatar's horizontal position immediately from its own held keys, continuously eased back toward the server's authoritative snapshots (`RECONCILE_BLEND` blends small errors, `PREDICT_SNAP_PX` hard-snaps large ones rather than smoothing through a real desync). The server remains the sole physics authority and the only thing that ever *decides* where anyone is — prediction only fills the gap *until* the next correction arrives. *Every other player* still renders purely from interpolated server snapshots, completely untouched by this. See `prediction_plan.md` for the staged design (this is its Phase 1: horizontal-only, no client physics engine) and the "Local-player prediction" status entry below for verification notes.
* **The shared movement/simulation model is single-sourced in [server/src/physics.ts](server/src/physics.ts)/[server/src/physics-bodies.ts](server/src/physics-bodies.ts) — never hand-mirrored.** World/player/platform constants (`WORLD_WIDTH`, `MOVE_SPEED`, `TICK_MS`, ...), shared types (`Point`, `Keys`), the ground-contact predicate (`isSupportingContact`), and the Matter.js body factories/movement function (`createPlatformBodies`, `applyMovement`, `createPlayerBody`, `createBoundaryBodies`) all live in these two modules and are imported by *both* `server.ts` and `client.ts`. This replaces the older pattern — seen through the interpolation feature — of the client keeping its own hand-copied constants (`SERVER_TICK_MS`, etc.) with a comment warning they "must stay in sync." That pattern was tolerable for values the client merely *displays*, but faithful prediction requires the local sim to run the *exact* model the server does; a hand-copied one only guarantees drift. The two-module split exists for a non-obvious reason — `physics.ts` is deliberately Matter-*runtime*-free (`import type * as Matter` only, plus constants/pure predicates), so importing it costs nothing in bundle size (empirically verified: 320 bytes / zero `matter-js` references in the compiled output); `physics-bodies.ts` holds the handful of functions that actually drive Matter bodies and pulls in the real runtime (~84KB minified — TypeScript `import type` is erased at compile time, but a *value* import of anything from a module that itself does `import Matter from "matter-js"` cannot be tree-shaken, so the whole library comes along). The server always pays that cost (it *is* the physics authority); Phase 1's client deliberately imports only from `physics.ts` to stay free of it. See both files' header comments for the full empirical rationale.

## Code-level style conventions (pinned 2026-06-07 — binding, don't deviate without updating this section)

A community reviewer (Mathium05, maintainer of Fermi/Melody/Harmony) read this codebase cold and accurately diagnosed it as feeling like "three or four people working on one codebase," despite being ~750 lines built solo. The real mechanism: this project is built across many independent Claude sessions, each starting with *zero memory* of the last. The macro architecture survived intact because it's written down above (and in the GDD) — but nobody had pinned the **micro**-decisions, so each session quietly re-derived its own (whichever idiom felt natural *that* session: `.className =` vs. `classList`, `Point` as data vs. class, how defensively to treat the server's own messages...). That's not "tech debt from going fast" — it's several different "authors" making different calls on the same kind of decision, which is precisely what fracturing *is*. The fix is the same one that's kept the architecture coherent: write it down, once, here.

* **DOM class manipulation: always `classList.add/remove/toggle`, never `.className =`.** `className =` clobbers every class already on the element — a latent bug the moment an element ever needs two classes for two different reasons (e.g. a selection-state class *and* a future hover-affordance class). `classList` methods only ever touch the class they name.
* **`id` only for elements that are (a) structurally unique to the whole page** — exactly one instance can ever exist (`join-screen`, `join-card`, `palette`) — **and (b) actually looked up by that id**, whether from CSS, `getElementById`/`querySelector`, or a `<label for>`. **Everything else — anything repeatable (swatches, list items, anything built in a loop) or purely a styling/structural hook — gets a class only.** Concretely: `colorPicker.id = "avatar-color-picker"` (client.ts) is dead weight — grep confirms it's neither styled (`#avatar-color-picker` doesn't exist in styles.css; only `.swatch-row` does) nor looked up anywhere. That's the smell of an id reached for out of habit rather than need; a cleanup pass should remove it.
* **Geometry stays data + free functions, never classes.** `Point` (and anything shaped like it) stays a plain `{x, y}` structural type, manipulated by free functions (`distance`, `perpendicularDistance`, `pointToSegmentDistance`, `rdpSimplify`, ...) — matching Matter.js's own idiom (`Matter.Vector` is a plain-object-plus-function-module, not a class) and avoiding allocation/dispatch overhead in code that runs every frame or every collision pair. Reserve `class` — and the `implements`/`satisfies` idioms that go with it — for the one place the *framework* requires it: `class Server implements Party.Server` / `Server satisfies Party.Worker`. That's PartyKit boilerplate, not a stylistic choice this project gets to make differently each session — don't let its presence there license reaching for classes elsewhere.
* **Canvas CSS size is always integer pixels.** Anything that writes to `canvas.style.width`/`height` (e.g. `fitCanvasToViewport`) must `Math.round()` first — sub-pixel CSS dimensions on a fixed-resolution canvas blur the entire render when the browser scales it.
* **Client-side validation posture toward the server: trust the shape, not the fields — and say so out loud when something fails even that.** The server is the sole source of truth (this project's whole server-authoritative premise) and already runs every inbound message through strict per-field validation (`isValidDraw`/`isValidPoint`/etc. — see gdd_partykit.md's "Schema Validation"/"Numbers Only" sections) before it ever broadcasts. The client must **not** re-derive and duplicate that same per-field logic for messages *coming from* the server — doing so creates two independent copies of "what does a valid Platform look like," and they *will* drift (this already happened: `platform_added`/`player_joined` get full per-field checks while `snapshot`/`world_state` get a bare `as PlatformSnapshot[]` cast, in the very same `switch`). Instead every case should run through one shared, minimal shape-check helper — "right `type`, right top-level keys, roughly-right primitive types" — and then trust the payload. Anything that *fails* even that minimal check is, by definition, not "untrusted user input" (that's the server's job to filter) but **a bug worth surfacing** — a stale client, a version-skewed deploy, a protocol typo — so log it (`console.warn`), don't silently swallow it. This is the *deliberate inverse* of the server's posture, and that asymmetry is correct, not inconsistent: the server silently drops malformed input because it's a hostile-input boundary (the GDD's security model — giving an attacker error feedback is itself a leak); the client's only inbound source is its own trusted server, so silence there just hides bugs from the one person who'd want to know about them.

**Ink budget redesign — room-wide quota + segment-level erase — is done** — a fast follow-up to the ink-budget feature directly above, prompted by the user almost as soon as it shipped: per-player tracking still let the *room* fill up with clutter even when no individual player looked over budget (the thing that actually bounds physics cost is total segments in the world — full stop, regardless of whose they are), and whole-platform erase meant a single right-click could remove far more geometry than the click visually targeted (erasing one end of a long winding stroke deleted the whole thing). > Whole-platform erase is **gone**, replaced by **segment-level** erase. `isValidEraseHit`/`isValidErase` now validate a *batch* — `{ type: "erase", hits: [{platformId, segmentIndex}, ...] }`, capped at `MAX_ERASE_HITS=500` (same order-of-magnitude rationale as `MAX_DRAW_POINTS`: legitimate drags, even fast ones crossing several overlapping platforms, land nowhere near it) — and `handleErase` groups hits by platform, fully removes each affected one (bodies out of the live Matter.js world, out of the registry, out of `room.storage`, `platform_removed` broadcast), then rebuilds 0–2 surviving sub-platforms via a new `splitPoints` helper: maximal contiguous runs of *non-removed* segments become fresh platforms with **brand-new random ids** but the **original owner and color carried through** — provenance survives a split even though identity (the id) doesn't need to. **Client-side entity interpolation is done** — players looked like they moved at a low frame rate: the server broadcasts position snapshots at 20Hz (`TICK_MS=50` in [server/src/server.ts](server/src/server.ts)) but the client renders at ~60fps, so the old render loop painted each server position for ~3 identical frames and then snapped to the next. The fix, planned in `interpolation_plan.md` and scoped entirely to [server/src/client.ts](server/src/client.ts) (no protocol or server changes): **client-side entity interpolation** — render the world `INTERP_DELAY_MS` (= `SERVER_TICK_MS * 2` = 100ms — one snapshot interval as the minimum buffer, a second as jitter/dropped-packet margin) in the past, and tween each avatar between the two real server snapshots that bracket that render time. The single-newest-snapshot field `latestPlayers` became `snapshotBuffer: Snapshot[]` (each entry stamped with `performance.now()` on arrival, pruned to just the window the current render needs), and a new free function `playersAt(renderTime)` — per this file's "geometry stays data + free functions, never classes" convention — finds the bracketing pair and linearly interpolates shared players' `x`/`y`, while explicitly handling the edges: before the buffer's start it shows the oldest snapshot outright, past its end it *holds* the last known position rather than extrapolating (holding is still "rendering server data"; extrapolating would cross into prediction), and a player present in only one bracket (mid-join/-leave) draws at its last/first known spot until it ages out. `frame()` now calls `drawPlayers(playersAt(performance.now() - INTERP_DELAY_MS))`. This is **strictly render-only** — `playersAt` only blends between two real server-reported positions, never simulates one, fully respecting "the client does no local physics or prediction."
>
> **Accepted tradeoff (deliberate, and a change from the original sketch):** the `TODO.md` idea this came from leaned toward interpolating *remote* players only (to avoid laggy local input) with local prediction as a possible separate follow-up. The actual plan chose the simpler path instead — interpolate *all* avatars uniformly, local included — accepting that the local player's own avatar now also lags its true server-side position by ~100ms. This is the known and intentional cost of this option; if it feels too laggy in practice, the documented next step is full client-side prediction (simulate locally, reconcile against server snapshots) — a meaningfully bigger lift that breaks the no-prediction convention, and explicitly *not* to be added preemptively.

**Local-player prediction (Phase 1 of `prediction_plan.md`) is done** — the interpolation feature directly above fixed remote players' choppiness but, by its own documented "accepted tradeoff," made the *local* avatar lag its own keypresses by `INTERP_DELAY_MS` (~100ms): the dominant felt-latency complaint interpolation's plan note predicted as the natural next request. `prediction_plan.md` lays out a staged fix and is explicit that this *intentionally* carves two scoped exceptions into conventions pinned elsewhere in this file — both are now also recorded as bullets in "Conventions established so far" above, and this entry is where the rationale and verification live.
>
> **Phase 0 (prerequisite — shipped as a structural deviation from the plan's single-file suggestion):** the plan called for one shared `physics.ts`; this instead splits into [server/src/physics.ts](server/src/physics.ts) (constants, `Point`/`Keys` types, the empirically-derived `isSupportingContact` predicate — all pure, `import type * as Matter` only) and [server/src/physics-bodies.ts](server/src/physics-bodies.ts) (`createPlatformBodies`, `applyMovement`, `createPlayerBody`, `createBoundaryBodies` — the functions that actually call into the runtime, `import Matter from "matter-js"`). The reason is a TypeScript/esbuild discovery made empirically mid-session: `import type` is erased at compile time, but a *value* import of anything from a module that itself does `import Matter from "matter-js"` (a CommonJS `require` under the hood) cannot be tree-shaken — the whole ~84KB-minified library rides along. A bundle importing only from `physics.ts` measured **320 bytes with zero `matter-js` references**; the moment a body-factory function entered the import graph, the full runtime did too. Splitting lets Phase 1 — which only needs constants and types — stay free of that cost, deferring it to a hypothetical Phase 2 (a real local Matter world). `server.ts` and `client.ts` both now import shared constants (`MOVE_SPEED`, `TICK_MS`, `WORLD_WIDTH`, `PLAYER_RADIUS`, ...), `Point`/`Keys`, and `isSupportingContact` from `physics.ts`; `server.ts` additionally imports the body factories from `physics-bodies.ts` (it always paid the Matter cost — it *is* the authority). Verified behavior-preserving via a temporary raw-WebSocket script (`verify-phase0-split-tmp.mjs`, deleted after use) sampling live snapshots: `y≈844.36`/`vy≈-9.85` matched the pre-refactor documented values exactly.
>
> **Phase 1 (shipped):** [server/src/client.ts](server/src/client.ts) gained `predictLocalX(dtMs)` — on every frame, it integrates the local avatar's held `keys` directly (`dir * MOVE_SPEED * (dtMs / TICK_MS)`, clamped to the world's side walls), faithfully rebuilding "where the server's direct-velocity horizontal model would have moved by now" without running any physics engine. `keys` moved from a `startGame`-local to a module-level `const` (mirroring `conn`) so this module-level function can read it every frame. The `"snapshot"` handler now also reconciles: it finds the local player in the fresh snapshot and eases `localX` toward `me.x` by `RECONCILE_BLEND=0.15` per snapshot — or, if `|error| > PREDICT_SNAP_PX=64`, hard-snaps instead, on the judgment that an error that large signals a real discontinuity (teleport, reconnect, knockback) rather than ordinary network jitter, and easing through it would just look like floating. `frame()` builds a fresh array from `playersAt(...)` — `.map()`, not in-place mutation as the plan's pseudocode sketched — substituting `localX` for the local entry's `x` only (`y` stays interpolated, the documented Phase 1 limitation: jumps/falls lag slightly behind input). The in-place approach was rejected after reading `playersAt`'s edge-case branches closely: they return snapshot objects *by reference* from `snapshotBuffer`, so writing `me.x = localX` would have permanently corrupted that buffered snapshot for every later frame's interpolation **and** reconciliation — a real bug the plan's sketch would have introduced, caught and fixed during implementation rather than ported faithfully.
>
> **The two convention exceptions** (both now permanently recorded in "Conventions established so far," not just here): **(1)** local prediction is a deliberate, narrowly-scoped carve-out of "the client does no local physics or prediction" (the verbatim phrase appears in the Phase 4 and interpolation entries above) — it predicts *only* the local avatar's `x`, is *continuously* corrected by server snapshots (never trusted over them), and leaves every remote player's rendering completely untouched; the server remains the sole authority exactly as before. **(2)** the movement model is now single-sourced in `physics.ts`/`physics-bodies.ts` and imported by both sides, replacing the older "hand-mirror server constants with a `// must stay in sync` comment" pattern this client used for purely-cosmetic values like `WORLD_WIDTH` through the interpolation feature — that pattern is fine for values the client only *displays*, but faithful prediction requires running the *exact* model the server does, and a hand-copied one only guarantees drift.
>
> **Accepted limitation (the plan's own "honest limitation," confirmed in testing, not eliminated):** because reconciliation eases toward a snapshot that's already ~RTT+tick old, there's a small standing error while continuously running — predicted position is slightly ahead of the (stale-by-the-time-it-arrives) authority the blend chases. On localhost this was measured as small, smooth, and one-directional (see verification below); the plan's documented fix for anyone who finds it bothersome under real latency is Phase 3 (input sequence numbers + reconciliation replay), deliberately not built now — **per the plan's explicit instruction to "stop at the earliest phase that feels responsive enough,"** Phase 1 alone felt responsive enough in testing (see below) to recommend stopping here; Phase 2 (a full local Matter world, "~tens of KB" client cost) and Phase 3 remain available, scoped, and ready if the user later wants more.
>
> Verified via `npx tsc --noEmit` (clean) and the live browser UI, reusing and extending this project's established `CanvasRenderingContext2D` monkey-patch technique (this time on both `.arc` and `.fillText`, to correlate sampled avatar positions with input-state and snapshot-arrival timing in one pass): the local avatar began moving **~28ms after keydown** — versus the prior ~100ms `INTERP_DELAY_MS` lag — across 671 sampled frames; wall-clamping landed at exactly `x=1584` (`WORLD_WIDTH - PLAYER_RADIUS`), matching the server's own clamp; reconciliation produced **56 corrections, every one <11px, every one easing forward** at snapshot-arrival cadence (~50ms) — never an inappropriate snap, never an overshoot, confirming the blend behaves as "a gentle pull," exactly the plan's intent. A second raw-WebSocket client (`verify-prediction-remote-tmp.mjs`, "Remote"/`#a3c4f3`, deleted after use) confirmed remote-player rendering is completely unaffected — correct identity/color, smooth interpolation, no ghost avatar after disconnect.
