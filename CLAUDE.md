# Mouse — Multiplayer Whiteboard Platformer

## Concept

A browser-based multiplayer game best described as **a whiteboard app meets Transformice**: players share a canvas where anyone can draw platforms in real time, and everyone's mouse avatars can physically jump and run on whatever gets drawn. The world is shaped by its players as they play.

## Stack

* **Client:** HTML5 Canvas + Matter.js
* **Networking:** PartyKit (`partysocket` client, `Party.Server` server class) — runs on Cloudflare's edge
* **Physics authority:** Server-authoritative — the PartyKit room runs Matter.js; clients send inputs and render state snapshots
* **Language:** TypeScript throughout (the eventual PartyKit project; the early prototype is plain JS/HTML for speed)
* **Deployment:** PartyKit managed platform (server) + Cloudflare Workers Static Assets (client), at `mice.ordulis.com`

## Conventions established so far

* **Drawn paths are raw `{x, y}` point arrays.** Physics platform bodies are generated *deterministically* from those arrays (currently: a chain of thin rectangle segments, one per consecutive point pair — robust against arbitrary squiggly/looping/zigzag freehand shapes, unlike `Matter.Bodies.fromVertices` which mishandles concave hulls).
* **Render from the point array, not from body geometry.** Pixel art is purely cosmetic — physics fidelity comes from the shared point array. This separation is established in the prototype's custom `requestAnimationFrame` render loop (deliberately *not* using `Matter.Render`, the debug renderer) and must carry through to the real multiplayer client, where rendering is driven by synced point arrays rather than physics internals.
* **Ramer–Douglas–Peucker simplification is deferred.** It's a network-bandwidth optimization for the drawing-sync phase (step 6), not something the single-player prototype needs — raw points give more stable collision geometry when there's no transmission cost.

## Current status

**Phase 1 (single-player prototype) is done** — [prototype/index.html](prototype/index.html) validates the core loop: drawing → physics body → avatar runs/jumps on it, including climbing hand-drawn slopes, standing on elevated platforms, falling off edges, and proper jump-gating (no infinite air-jumps). Verified via automated browser testing (simulated draw/input events + frame-by-frame physics-state sampling).

**Phase 2 (PartyKit project scaffold) is done** — [server/](server/) is a scaffolded TypeScript PartyKit project with a minimal `Party.Server` ([server/src/server.ts](server/src/server.ts)) whose `onConnect` sends each joiner a personalized welcome message (`Welcome to room "<roomId>", you are <connectionId>`). Verified locally: `npm run dev` boots the room on `http://127.0.0.1:1999`, and a raw WebSocket test client connecting to `/parties/main/<room>` receives the welcome message.

**Phase 3 (server-authoritative physics loop) is done** — [server/src/server.ts](server/src/server.ts) now runs a Matter.js world server-side: `onStart` builds the engine/gravity/ground, `onConnect`/`onClose` add/remove a circle body per connection (mirroring the prototype's avatar), and a ~20Hz `setInterval` tick steps the simulation and broadcasts `{ type: "snapshot", players: [{id,x,y,vx,vy}], tick }` to every client. [server/src/client.ts](server/src/client.ts) is a minimal canvas client that connects via `PartySocket`, receives snapshots, and renders player circles + the static ground — purely server-driven, no client-side physics or input yet. Verified locally by sampling 120 broadcasts: a freshly-connected player fell from its spawn point under gravity and came to rest exactly on the ground, confirmed tick-over-tick from real server simulation (not a static render).

**Phase 4 (player input pipeline) is done** — [server/src/client.ts](server/src/client.ts) captures keyboard input (arrow keys / WASD to run, Up/W/Space to jump) and sends `{ type: "input", keys: {left, right, jump} }` only on state change; [server/src/server.ts](server/src/server.ts) validates the message shape via a type guard, stores per-connection key state, and each tick applies the prototype's exact movement logic — direct-velocity horizontal movement plus a one-shot, ground-gated jump reusing the empirically-derived `isSupportingContact` sign convention — to that connection's body. Still fully server-authoritative and snapshot-driven; the client does no local physics or prediction. Verified end-to-end by sampling live snapshot broadcasts while programmatically driving input: horizontal movement, jump impulse (peak `vy≈-9.85`), mid-air jump gating (a second press while airborne produced no fresh impulse), landing, and jump re-arming after landing (a fresh press immediately post-landing peaked at the same `vy≈-9.85`) all behaved correctly through the real network pipeline.

**Phase 5 (second player / multiplayer sync) is done** — each connection is now assigned a placeholder cheese-themed username server-side (`pickUsername` in [server/src/server.ts](server/src/server.ts), matching the GDD's own `"Mozzarella"` example — a real lobby/picker is deferred to Phase 7). On `onConnect`, the room sends the joiner a `world_state` message describing all *existing* players' live positions and usernames (so they don't see a blank world or wait for the next tick), then broadcasts `player_joined` to *everyone including the joiner itself* — since `world_state` only covers pre-existing players, this broadcast is how a joiner learns its own assigned name. `onClose` broadcasts `player_left` and prunes the body as before. [server/src/client.ts](server/src/client.ts) now tracks an `id → username` roster from these messages and renders each avatar with a name label, visually distinguishing the local player (green fill + `"(you)"`) from others (yellow fill). Verified by opening extra raw-`WebSocket` connections to the same room: a 3rd joiner's `world_state` showed the 2nd joiner still mid-fall (not yet landed) — proving late joiners see everyone's *current live* position with no flicker/teleport — and roster add/remove tracked correctly through full join/leave cycles.

**Phase 6 (drawing sync) is done** — the full draw pipeline now works end-to-end. [server/src/client.ts](server/src/client.ts) captures freehand strokes (`mousedown`/`mousemove`/`mouseup`, converting CSS-viewport coordinates into the fixed world buffer via `canvasPoint` — necessary because, unlike the prototype, this client's canvas is CSS-scaled to fit the viewport), simplifies them with Ramer-Douglas-Peucker (`rdpSimplify`, the bandwidth optimization the prototype deferred — see "Conventions" above), and sends `{ type: "draw", points, color }` with a color chosen from a small preset palette UI. [server/src/server.ts](server/src/server.ts) validates every point per the GDD's "Numbers Only" security guidance (`isValidDraw`/`isValidPoint` — rejects non-finite numbers, out-of-bounds coordinates, extra keys, malformed colors), enforces physics-spam limits (`DRAW_COOLDOWN_MS=1000`, `MAX_PLATFORMS_PER_PLAYER=10`), builds deterministic chain-of-thin-rectangle bodies (`createPlatformBodies`, ported from the prototype's `pointsToBodies`), persists each platform to `this.room.storage` under `platform:{id}` keys, and restores them all in an `async onStart` (which PartyKit guarantees completes before the first `onConnect`). New platforms broadcast as `platform_added` to *everyone including the drawer* — the same "no special-cased local preview" pattern Phase 5 established for `player_joined` — and `world_state` now includes existing platforms for late joiners. The client regenerates purely-cosmetic geometry from synced point arrays (`drawPlatformPath`/`drawPlatforms`, plus a live in-progress-stroke preview), never from physics internals — keeping the rendering convention established in Phase 1 intact across the network boundary.

**Phase 7 (lobby logic) is done** — round logic stayed shelved (see below) so a real lobby could ship before deployment. [server/src/client.ts](server/src/client.ts) now shows a join screen (`buildJoinScreen`) before ever opening a connection: a username input, an avatar-color swatch picker (reusing the existing `PALETTE_COLORS`), and a room-code field that's auto-generated (`generateRoomCode`, drawn from an ambiguity-free `ROOM_CODE_CHARS` alphabet that excludes `0/O/1/I/L`) or pre-filled from a `?room=` URL param (`roomCodeFromUrl`). Submitting updates the URL via `history.replaceState` — making it shareable — and calls `startGame(roomId, identity)`, which is when the `PartySocket` connection is actually opened (deferred from module load, so the lobby can collect identity/room *first*). The chosen `username`/`color` travel to the server as `PartySocket` `query` params, read in `onConnect(conn, ctx)` via `new URL(ctx.request.url).searchParams`, run through `sanitizeUsername`/`sanitizeColor` ([server/src/server.ts](server/src/server.ts) — strips control characters, trims, caps at `MAX_USERNAME_LENGTH=20`, validates hex colors against `COLOR_PATTERN`, and falls back to a cheese name / `DEFAULT_AVATAR_COLOR` for anything missing or invalid, satisfying the GDD's "XSS via Usernames" guidance at the trust boundary), and stored via `connection.setState()` per the GDD's "Connection State" guidance — `pickUsername`'s placeholder cheese-name system from Phase 5 now serves purely as that fallback. Each avatar renders in its own chosen color (`drawPlayers`), with a `"(you)"` marker and green outline distinguishing the local player.

> Verified end-to-end: the join screen renders correctly (title, tagline, inputs, swatches, pre-filled room code, hint, button — screenshot-confirmed); submitting it produces a shareable `?room=<CODE>` URL and connects with the chosen identity (a temporary debug hook confirmed the local roster/player entry exactly matched the picked username/color); a second raw-`WebSocket` client joining the same room code with different identity query params was correctly recognized as independent by both sides (`world_state` + `player_joined` + roster sync stayed correct in both directions); and five deliberately-bad connect attempts — control characters plus a 100+ character name, a whitespace-only name, a CSS color name (`"red"`), shorthand hex (`"#fff"`), and missing params entirely — were all sanitized exactly as designed (cheese-name and/or `DEFAULT_AVATAR_COLOR` fallbacks, hard length cap at 20). `grep` confirmed zero uses of `innerHTML`/`outerHTML`/`insertAdjacentHTML` anywhere in the client — every dynamic string reaches the page via `textContent` or canvas `fillText`, neither of which parses markup, so unsanitized strings can only ever render as inert text. **The game is live.** The PartyKit server is deployed at [https://mice.shisatum.partykit.dev](https://mice.shisatum.partykit.dev) (`partykit.json`'s `"name"` was changed from the scaffold default `"server"` to `"mice"`, since that field directly determines the `mice.[username].partykit.dev` subdomain the GDD expects — `npx partykit deploy` then publishes both the room logic *and* the bundled static client in one step, per `partykit.json`'s `serve: { path: "public", build: "src/client.ts" }`). The client is separately deployed via Cloudflare Workers Static Assets at [https://mice.thardobodol.workers.dev](https://mice.thardobodol.workers.dev) — a new [server/wrangler.toml](server/wrangler.toml) points `[assets].directory` straight at the existing `server/public/` folder (the same PartyKit-built bundle, no separate build pipeline needed), and `npx wrangler deploy` uploads it. This works *because* `declare const PARTYKIT_HOST: string` in [server/src/client.ts](server/src/client.ts) is a compile-time constant — PartyKit's bundler bakes the literal string `"mice.shisatum.partykit.dev"` into `public/dist/client.js`, so the Cloudflare-hosted static client connects cross-origin (over WSS) straight to the PartyKit room regardless of where it's served from. This is exactly the architecture the GDD intends (two separate origins, client and server deployed independently); PartyKit's managed platform doesn't support custom domains, so the `.partykit.dev` URL is the fixed server endpoint, while a custom domain like `mice.ordulis.com` could still be pointed at the Cloudflare Workers deployment later via its dashboard (tracked as an optional item in TODO.md).
