# Mouse — Multiplayer Whiteboard Platformer

## Concept

A browser-based multiplayer game best described as **a whiteboard app meets Transformice**: players share a canvas where anyone can draw platforms in real time, and everyone's mouse avatars can physically jump and run on whatever gets drawn. The world is shaped by its players as they play.

## Stack

* **Client:** HTML5 Canvas + Matter.js
* **Networking:** PartyKit (`partysocket` client, `Party.Server` server class) — runs on Cloudflare's edge
* **Physics authority:** Server-authoritative — the PartyKit room runs Matter.js; clients send inputs and render state snapshots
* **Language:** TypeScript throughout (the eventual PartyKit project; the early prototype is plain JS/HTML for speed)
* **Deployment:** PartyKit managed platform (server) + Cloudflare Workers Static Assets (client)

## Conventions established so far

* **Drawn paths are raw `{x, y}` point arrays.** Physics platform bodies are generated *deterministically* from those arrays (currently: a chain of thin rectangle segments, one per consecutive point pair — robust against arbitrary squiggly/looping/zigzag freehand shapes, unlike `Matter.Bodies.fromVertices` which mishandles concave hulls).
* **Render from the point array, not from body geometry.** Pixel art is purely cosmetic — physics fidelity comes from the shared point array. This separation is established in the prototype's custom `requestAnimationFrame` render loop (deliberately *not* using `Matter.Render`, the debug renderer) and must carry through to the real multiplayer client, where rendering is driven by synced point arrays rather than physics internals.
* **Ramer–Douglas–Peucker simplification is deferred.** It's a network-bandwidth optimization for the drawing-sync phase (step 6), not something the single-player prototype needs — raw points give more stable collision geometry when there's no transmission cost.

## Code-level style conventions (pinned 2026-06-07 — binding, don't deviate without updating this section)

A community reviewer (Mathium05, maintainer of Fermi/Melody/Harmony) read this codebase cold and accurately diagnosed it as feeling like "three or four people working on one codebase," despite being ~750 lines built solo. The real mechanism: this project is built across many independent Claude sessions, each starting with *zero memory* of the last. The macro architecture survived intact because it's written down above (and in the GDD) — but nobody had pinned the **micro**-decisions, so each session quietly re-derived its own (whichever idiom felt natural *that* session: `.className =` vs. `classList`, `Point` as data vs. class, how defensively to treat the server's own messages...). That's not "tech debt from going fast" — it's several different "authors" making different calls on the same kind of decision, which is precisely what fracturing *is*. The fix is the same one that's kept the architecture coherent: write it down, once, here.

* **DOM class manipulation: always `classList.add/remove/toggle`, never `.className =`.** `className =` clobbers every class already on the element — a latent bug the moment an element ever needs two classes for two different reasons (e.g. a selection-state class *and* a future hover-affordance class). `classList` methods only ever touch the class they name.
* **`id` only for elements that are (a) structurally unique to the whole page** — exactly one instance can ever exist (`join-screen`, `join-card`, `palette`) — **and (b) actually looked up by that id**, whether from CSS, `getElementById`/`querySelector`, or a `<label for>`. **Everything else — anything repeatable (swatches, list items, anything built in a loop) or purely a styling/structural hook — gets a class only.** Concretely: `colorPicker.id = "avatar-color-picker"` (client.ts) is dead weight — grep confirms it's neither styled (`#avatar-color-picker` doesn't exist in styles.css; only `.swatch-row` does) nor looked up anywhere. That's the smell of an id reached for out of habit rather than need; a cleanup pass should remove it.
* **Geometry stays data + free functions, never classes.** `Point` (and anything shaped like it) stays a plain `{x, y}` structural type, manipulated by free functions (`distance`, `perpendicularDistance`, `pointToSegmentDistance`, `rdpSimplify`, ...) — matching Matter.js's own idiom (`Matter.Vector` is a plain-object-plus-function-module, not a class) and avoiding allocation/dispatch overhead in code that runs every frame or every collision pair. Reserve `class` — and the `implements`/`satisfies` idioms that go with it — for the one place the *framework* requires it: `class Server implements Party.Server` / `Server satisfies Party.Worker`. That's PartyKit boilerplate, not a stylistic choice this project gets to make differently each session — don't let its presence there license reaching for classes elsewhere.
* **Canvas CSS size is always integer pixels.** Anything that writes to `canvas.style.width`/`height` (e.g. `fitCanvasToViewport`) must `Math.round()` first — sub-pixel CSS dimensions on a fixed-resolution canvas blur the entire render when the browser scales it.
* **Client-side validation posture toward the server: trust the shape, not the fields — and say so out loud when something fails even that.** The server is the sole source of truth (this project's whole server-authoritative premise) and already runs every inbound message through strict per-field validation (`isValidDraw`/`isValidPoint`/etc. — see gdd_partykit.md's "Schema Validation"/"Numbers Only" sections) before it ever broadcasts. The client must **not** re-derive and duplicate that same per-field logic for messages *coming from* the server — doing so creates two independent copies of "what does a valid Platform look like," and they *will* drift (this already happened: `platform_added`/`player_joined` get full per-field checks while `snapshot`/`world_state` get a bare `as PlatformSnapshot[]` cast, in the very same `switch`). Instead every case should run through one shared, minimal shape-check helper — "right `type`, right top-level keys, roughly-right primitive types" — and then trust the payload. Anything that *fails* even that minimal check is, by definition, not "untrusted user input" (that's the server's job to filter) but **a bug worth surfacing** — a stale client, a version-skewed deploy, a protocol typo — so log it (`console.warn`), don't silently swallow it. This is the *deliberate inverse* of the server's posture, and that asymmetry is correct, not inconsistent: the server silently drops malformed input because it's a hostile-input boundary (the GDD's security model — giving an attacker error feedback is itself a leak); the client's only inbound source is its own trusted server, so silence there just hides bugs from the one person who'd want to know about them.

## Current status

**Phase 1 (single-player prototype) is done** — [prototype/index.html](prototype/index.html) validates the core loop: drawing → physics body → avatar runs/jumps on it, including climbing hand-drawn slopes, standing on elevated platforms, falling off edges, and proper jump-gating (no infinite air-jumps). Verified via automated browser testing (simulated draw/input events + frame-by-frame physics-state sampling).

**Phase 2 (PartyKit project scaffold) is done** — [server/](server/) is a scaffolded TypeScript PartyKit project with a minimal `Party.Server` ([server/src/server.ts](server/src/server.ts)) whose `onConnect` sends each joiner a personalized welcome message (`Welcome to room "<roomId>", you are <connectionId>`). Verified locally: `npm run dev` boots the room on `http://127.0.0.1:1999`, and a raw WebSocket test client connecting to `/parties/main/<room>` receives the welcome message.

**Phase 3 (server-authoritative physics loop) is done** — [server/src/server.ts](server/src/server.ts) now runs a Matter.js world server-side: `onStart` builds the engine/gravity/ground, `onConnect`/`onClose` add/remove a circle body per connection (mirroring the prototype's avatar), and a ~20Hz `setInterval` tick steps the simulation and broadcasts `{ type: "snapshot", players: [{id,x,y,vx,vy}], tick }` to every client. [server/src/client.ts](server/src/client.ts) is a minimal canvas client that connects via `PartySocket`, receives snapshots, and renders player circles + the static ground — purely server-driven, no client-side physics or input yet. Verified locally by sampling 120 broadcasts: a freshly-connected player fell from its spawn point under gravity and came to rest exactly on the ground, confirmed tick-over-tick from real server simulation (not a static render).

**Phase 4 (player input pipeline) is done** — [server/src/client.ts](server/src/client.ts) captures keyboard input (arrow keys / WASD to run, Up/W/Space to jump) and sends `{ type: "input", keys: {left, right, jump} }` only on state change; [server/src/server.ts](server/src/server.ts) validates the message shape via a type guard, stores per-connection key state, and each tick applies the prototype's exact movement logic — direct-velocity horizontal movement plus a one-shot, ground-gated jump reusing the empirically-derived `isSupportingContact` sign convention — to that connection's body. Still fully server-authoritative and snapshot-driven; the client does no local physics or prediction. Verified end-to-end by sampling live snapshot broadcasts while programmatically driving input: horizontal movement, jump impulse (peak `vy≈-9.85`), mid-air jump gating (a second press while airborne produced no fresh impulse), landing, and jump re-arming after landing (a fresh press immediately post-landing peaked at the same `vy≈-9.85`) all behaved correctly through the real network pipeline.

**Phase 5 (second player / multiplayer sync) is done** — each connection is now assigned a placeholder cheese-themed username server-side (`pickUsername` in [server/src/server.ts](server/src/server.ts), matching the GDD's own `"Mozzarella"` example — a real lobby/picker is deferred to Phase 7). On `onConnect`, the room sends the joiner a `world_state` message describing all *existing* players' live positions and usernames (so they don't see a blank world or wait for the next tick), then broadcasts `player_joined` to *everyone including the joiner itself* — since `world_state` only covers pre-existing players, this broadcast is how a joiner learns its own assigned name. `onClose` broadcasts `player_left` and prunes the body as before. [server/src/client.ts](server/src/client.ts) now tracks an `id → username` roster from these messages and renders each avatar with a name label, visually distinguishing the local player (green fill + `"(you)"`) from others (yellow fill). Verified by opening extra raw-`WebSocket` connections to the same room: a 3rd joiner's `world_state` showed the 2nd joiner still mid-fall (not yet landed) — proving late joiners see everyone's *current live* position with no flicker/teleport — and roster add/remove tracked correctly through full join/leave cycles.

**Phase 6 (drawing sync) is done** — the full draw pipeline now works end-to-end. [server/src/client.ts](server/src/client.ts) captures freehand strokes (`mousedown`/`mousemove`/`mouseup`, converting CSS-viewport coordinates into the fixed world buffer via `canvasPoint` — necessary because, unlike the prototype, this client's canvas is CSS-scaled to fit the viewport), simplifies them with Ramer-Douglas-Peucker (`rdpSimplify`, the bandwidth optimization the prototype deferred — see "Conventions" above), and sends `{ type: "draw", points, color }` with a color chosen from a small preset palette UI. [server/src/server.ts](server/src/server.ts) validates every point per the GDD's "Numbers Only" security guidance (`isValidDraw`/`isValidPoint` — rejects non-finite numbers, out-of-bounds coordinates, extra keys, malformed colors), enforces physics-spam limits (`DRAW_COOLDOWN_MS=1000`, `MAX_PLATFORMS_PER_PLAYER=10`), builds deterministic chain-of-thin-rectangle bodies (`createPlatformBodies`, ported from the prototype's `pointsToBodies`), persists each platform to `this.room.storage` under `platform:{id}` keys, and restores them all in an `async onStart` (which PartyKit guarantees completes before the first `onConnect`). New platforms broadcast as `platform_added` to *everyone including the drawer* — the same "no special-cased local preview" pattern Phase 5 established for `player_joined` — and `world_state` now includes existing platforms for late joiners. The client regenerates purely-cosmetic geometry from synced point arrays (`drawPlatformPath`/`drawPlatforms`, plus a live in-progress-stroke preview), never from physics internals — keeping the rendering convention established in Phase 1 intact across the network boundary.

**Phase 7 (lobby logic) is done** — round logic stayed shelved (see below) so a real lobby could ship before deployment. [server/src/client.ts](server/src/client.ts) now shows a join screen (`buildJoinScreen`) before ever opening a connection: a username input, an avatar-color swatch picker (reusing the existing `PALETTE_COLORS`), and a room-code field that's auto-generated (`generateRoomCode`, drawn from an ambiguity-free `ROOM_CODE_CHARS` alphabet that excludes `0/O/1/I/L`) or pre-filled from a `?room=` URL param (`roomCodeFromUrl`). Submitting updates the URL via `history.replaceState` — making it shareable — and calls `startGame(roomId, identity)`, which is when the `PartySocket` connection is actually opened (deferred from module load, so the lobby can collect identity/room *first*). The chosen `username`/`color` travel to the server as `PartySocket` `query` params, read in `onConnect(conn, ctx)` via `new URL(ctx.request.url).searchParams`, run through `sanitizeUsername`/`sanitizeColor` ([server/src/server.ts](server/src/server.ts) — strips control characters, trims, caps at `MAX_USERNAME_LENGTH=20`, validates hex colors against `COLOR_PATTERN`, and falls back to a cheese name / `DEFAULT_AVATAR_COLOR` for anything missing or invalid, satisfying the GDD's "XSS via Usernames" guidance at the trust boundary), and stored via `connection.setState()` per the GDD's "Connection State" guidance — `pickUsername`'s placeholder cheese-name system from Phase 5 now serves purely as that fallback. **The game is live.** The PartyKit server is deployed to PartyKit's managed platform — `partykit.json`'s `"name"` was changed from the scaffold default `"server"` to `"mice"`, since that field directly determines the deployed `mice.[partykit-username].partykit.dev` subdomain — and `npx partykit deploy` publishes both the room logic *and* the bundled static client in one step, per `partykit.json`'s `serve: { path: "public", build: "src/client.ts" }`. The client is separately deployed via Cloudflare Workers Static Assets at a generated `mice.[cloudflare-account].workers.dev` subdomain — a new [server/wrangler.toml](server/wrangler.toml) points `[assets].directory` straight at the existing `server/public/` folder (the same PartyKit-built bundle, no separate build pipeline needed), and `npx wrangler deploy` uploads it. This works *because* `declare const PARTYKIT_HOST: string` in [server/src/client.ts](server/src/client.ts) is a compile-time constant — PartyKit's bundler bakes the deployed PartyKit subdomain into `public/dist/client.js` as a literal string at build time, so the Cloudflare-hosted static client connects cross-origin (over WSS) straight to the PartyKit room regardless of where it's served from. This is exactly the architecture the GDD intends (two separate origins, client and server deployed independently); PartyKit's managed platform doesn't support custom domains, so the `.partykit.dev` URL is the fixed server endpoint — a custom domain could in principle be pointed at the Cloudflare Workers deployment later via its dashboard, though this project isn't using one. (Live URLs are intentionally not published in this doc — ask the maintainer if you'd like the link.)

**Walls & erase feature is done** — two community-facing additions picked up once the (now-public) GitHub repo was in good shape. [server/src/server.ts](server/src/server.ts)'s `onStart` now adds `leftWall`/`rightWall`/`ceiling` static bodies (alongside the existing ground) bounding the `WORLD_WIDTH x WORLD_HEIGHT` play space, all sharing `label: "platform"` so the existing, empirically-derived `isSupportingContact` collision logic (Phase 1) handles them with zero special-casing — hitting a ceiling from below is just the geometric mirror of "bumping a platform's underside," which that logic already correctly excludes from counting as "landed." Separately, the game now supports **erasing platforms** — and by deliberate design (discussed with the user before implementing), **anyone can erase anything**: it fits the "world is shaped by its players" theme established above, and the griefing trade-off is easily reversible later to an owner-only check (`isValidErase`'s doc comment notes there's no owner check to *bypass* — the permission model already allows it). Right-click (`contextmenu`, with `event.preventDefault()` to suppress the native browser menu) hit-tests the *closest* platform under the cursor — `findPlatformAt` plus a new `pointToSegmentDistance` helper (distance-to-finite-*segment*, distinct from the RDP-simplification-only `perpendicularDistance`'s distance-to-infinite-*line*) — within `ERASE_HIT_TOLERANCE = PLATFORM_THICKNESS/2 + 6`, then sends `{ type: "erase", id }`. ("Closest" was chosen over z-order/topmost because `Map` iteration order for `platforms` reflects each client's own arrival order — storage-listing order for late joiners vs. live-broadcast order for new draws — and isn't globally consistent across clients.) The server validates the message shape (`isValidErase`), rate-limits via `ERASE_COOLDOWN_MS=250` (looser than `DRAW_COOLDOWN_MS=1000`, since erasing doesn't strain physics — it's purely a storage/broadcast-spam guard, not a gameplay gate), removes the platform's bodies from the live Matter.js world, drops it from the registry, deletes its persisted `room.storage` record, and broadcasts `platform_removed` to *everyone including the eraser* — the same "no special-cased local preview" pattern `draw`/`platform_added` established in Phase 6. Each player's own platforms render with a dashed `#6ee7b7` halo (`drawPlatformPath`'s new `isOwn` branch, reusing the existing "(you)" accent color rather than inventing new visual language) so they can find and erase their own work if they hit `MAX_PLATFORMS_PER_PLAYER`.
