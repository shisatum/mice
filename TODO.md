# Build Checklist

Chronological checklist mirroring the GDD's "Recommended Build Order" ([gdd_partykit.md](gdd_partykit.md)).

**How to use this file:**
- Check it at the start of every session to see where things stand.
- Check items off (`[x]`) as you complete them.
- Phases are expanded into sub-tasks only once you start them — expand the next phase's checkbox into concrete sub-tasks when you begin it, since detailed planning too far ahead tends to drift from reality.

---

## Phase 1 — Single-player prototype

> Canvas + Matter.js, no networking. Validates the core fun: drawing → physics body → mouse avatar can jump on it.

- [x] Set up `prototype/index.html` — single self-contained file, Matter.js via CDN (`matter-js@0.20.0`), no build step
- [x] Drawing capture: mousedown/mousemove/mouseup → freehand path as `{x, y}[]`
- [x] Path → physics body: chain of thin static rectangle segments along the drawn path
- [x] Avatar body: circle with locked rotation (`inertia: Infinity`) so it slides instead of rolling
- [x] Controls: arrow keys / WASD → horizontal velocity + one-shot jump velocity
- [x] Ground detection: `collisionStart`/`collisionEnd` → `groundContacts` counter → `grounded` flag (gates jumping)
- [x] Render loop: custom `requestAnimationFrame`, draw platforms from their point arrays + avatar as a circle (not `Matter.Render`)
- [x] Manually verify: draw platforms of various shapes, confirm avatar runs/jumps on them without falling through or infinite-air-jumping

> **Verified** (via automated browser testing — drawing simulated mouse paths, sampling physics state every frame): the avatar climbs hand-drawn slopes, stands on elevated drawn platforms, falls off edges, and jumps with a clean ~167px arc. `grounded` correctly gates jumping (no infinite air-jumps).
>
> **Bug found & fixed during verification:** the initial `isSupportingContact` check only tested whether the contact normal was vertical, not which side the platform was on — so bumping your head on a platform's underside mid-jump could be miscounted as "landing," refreshing the jump at the worst moment. Fixed by checking the normal's sign relative to which body is the player (Matter 0.20's SAT normal is not a simple "bodyA → bodyB" center-to-center vector — the correct sign convention was derived empirically and is documented inline in `isSupportingContact`).

## Phase 3 — Server-authoritative physics loop

- [x] Port a minimal physics setup (engine, gravity, static ground) into [server/src/server.ts](server/src/server.ts), running on a `setInterval` tick at ~20Hz
- [x] `onStart`: create the Matter.js engine/world + ground; `onConnect`: add a player body to the world (mirroring the prototype's circle avatar with locked rotation); `onClose`: remove it
- [x] Broadcast `snapshot` messages (`{ type: "snapshot", players: [{id,x,y,vx,vy}], tick }`) each tick via `this.room.broadcast`
- [x] Build a minimal client ([server/src/client.ts](server/src/client.ts) + canvas in `public/index.html`) that connects, receives snapshots, and renders player position(s) — no input/controls yet, purely observing server-driven movement

> **Verified** by sampling 120 snapshot broadcasts via a temporary `window.__debug` hook (same pattern as Phase 1): the player spawned at `y≈251.66` falling (`vy≈0.83`), and within ~30 ticks settled at `y≈844.36` with `vy=0` — exactly the calculated resting position on the ground (ground top at `y=860`, minus the player's 16px radius). 120 samples spanning ticks 2682–2801 confirmed a steady ~20Hz broadcast. Confirmed server-authoritative (not a static render) since the position genuinely changes tick-over-tick driven purely by the room's Matter.js simulation. Debug hook fully removed afterward (verified via Grep — 0 matches for `__debug|TEMP DEBUG`).
>
> **Bug found & fixed during setup:** the GDD's own example code calls `Matter.Engine.update(engine, 50)` directly at the 20Hz tick rate, but Matter.js warns that delta arguments above ~16.667ms risk instability/tunneling through thin bodies (which matters a lot once Phase 6 introduces thin drawn-platform segments). Fixed by sub-stepping the engine at a fixed ~60Hz internally (3 sub-steps of `1000/60`ms per 50ms tick) while still broadcasting snapshots at 20Hz — confirmed the warning no longer appears on a clean server run.
>
> Added a `server-dev` entry to [.claude/launch.json](.claude/launch.json) (backed by `server/dev.cmd`, since the Node.js install directory isn't on the preview tool's spawn `PATH` — the wrapper script prepends it) so the PartyKit dev server can be driven through the browser-preview tooling like the prototype.

## Phase 4 — Player input pipeline

- [x] Client sends `input` messages (`{ left, right, jump }`); server applies them to the player's body
- [x] Server tracks per-connection key state (`{ left, right, jump }`) and applies the same movement logic the prototype used (direct velocity, one-shot gated jump) to that connection's body each tick — see `applyInput` in [server/src/server.ts](server/src/server.ts)
- [x] Client adds keyboard capture (arrow keys / WASD, up/W/Space to jump) and sends `input` messages on change — render loop stays snapshot-driven (no client-side prediction yet); added an on-screen control hint
- [x] Manually verify: moving/jumping the local player is visible in the canvas, server-authoritatively, with correct ground-gating (reusing the prototype's empirically-derived `isSupportingContact` sign convention)

> **Verified** end-to-end via a temporary `window.__debug` hook sampling snapshot broadcasts while programmatically driving `setKey`:
> - **Horizontal movement**: resting `{x:800, vx:0}` → after holding right ~1s, `{x:1082.2, vx:4.26}` (accelerating toward `MOVE_SPEED=5` under `frictionAir`) → on release, `{x:1082.2, vx:0}`. Proves the full round trip: keypress → `input` message → server validation → per-connection key state → `applyInput` → `Matter.Body.setVelocity` → physics → broadcast → client render.
> - **Jump + mid-air gating**: grounded `{vy:0, y:844.36}` → jump impulse peaks at `vy≈-9.85` (≈ `-JUMP_SPEED=11` reduced by one tick of gravity/sub-stepping before the snapshot is taken) → rises and decelerates under gravity (`vy:-5.57` → `vy:-0.91` near apex) → a second jump press while still airborne produced **no** fresh `-11` impulse (correctly gated, continued its existing arc) → lands back at `{vy:0, y:844.36}`.
> - **Re-arming after landing**: immediately after landing, a fresh jump press peaked at `vy≈-9.85` again — identical to the first jump — proving `groundContacts`/`jumpHeld` correctly re-arm the one-shot jump once grounded again.
>
> Debug hook fully removed afterward (verified via Grep — 0 matches for `__debug|TEMP DEBUG`).
>
> **False alarm caught during verification:** an early test run showed the player frozen mid-test (`landed`/`secondJump`/`landedAgain` samples all identical, ticks barely advancing despite seconds of elapsed time). Root cause was the *test harness*, not the game: the `dbg.samples` ring buffer was capped at 400 entries and had filled up across back-to-back `preview_eval` runs, so `latestFor` kept returning the last-recorded (stale) sample instead of fresh data. Re-running with `dbg.samples.length = 0` resets between phases produced clean, consistent results — no bug in `applyInput`/ground-detection.

- [x] Server broadcasts `platform_added` to *everyone including the drawer* (`{ type: "platform_added", id, points, color, owner }`) — same "no special-cased local preview" pattern as Phase 5's `player_joined`; `world_state` now also includes existing platforms for late joiners

- [x] Manually verify: drawing creates a real collidable platform (avatar runs/jumps on it), syncs to other clients live and via `world_state` on join, persists across a server restart, and rejects invalid/spammy input

The avatar then walked under it, fell onto it, and **rested at `y≈779.36`** — exactly the calculated resting spot on the platform's surface (not the ground's `y≈844`), proving the server generated real, correctly-positioned collision bodies from the drawn points (not just cosmetic strokes). ## Walls & erase feature

> Two community-facing additions picked up after the GitHub repo went public: world boundaries (so players can't run/fall off the edge of the world into the void) and a shared erase tool (so the canvas doesn't fill up with permanent clutter — fits the "world is shaped by its players" theme).

- [x] Server: add static `leftWall`/`rightWall`/`ceiling` bodies (alongside the existing ground) bounding the `WORLD_WIDTH x WORLD_HEIGHT` play space — all sharing `label: "platform"` so the existing `isSupportingContact` collision logic (empirically derived in Phase 1, unchanged since) handles them uniformly with zero special-casing
- [x] Server: `erase` message validation (`isValidErase`) + `handleErase` — removes the platform's bodies from the live Matter.js world, drops it from the registry, deletes its persisted `room.storage` record, and broadcasts `platform_removed` to everyone (including the eraser — same "no special-cased local preview" pattern as `draw`/`platform_added`); rate-limited via `ERASE_COOLDOWN_MS=250` (looser than `DRAW_COOLDOWN_MS=1000`, since erasing doesn't strain physics — purely a storage/broadcast-spam guard, not a gameplay gate) — *whole-platform `isValidErase`/`handleErase` were later rewritten for batched, segment-level erase in the redesign below; `ERASE_COOLDOWN_MS` itself didn't change, but what it gates did (per-click → per-drag-gesture)*
- [x] Client: right-click capture (`contextmenu`, with `event.preventDefault()` to suppress the native browser menu) + closest-platform hit-testing (`findPlatformAt`, using a new `pointToSegmentDistance` helper — distance to a finite *segment*, vs. the existing `perpendicularDistance`'s distance to an infinite *line* used only for RDP simplification — within `ERASE_HIT_TOLERANCE = PLATFORM_THICKNESS/2 + 6`) — *`findPlatformAt` was later replaced by the finer-grained `findSegmentAt` in the redesign below; `pointToSegmentDistance`/`ERASE_HIT_TOLERANCE` carried over unchanged*
- [x] ~~Client: highlight the local player's own platforms with a dashed halo (`OWN_PLATFORM_HIGHLIGHT = "#6ee7b7"`, reusing the existing "(you)" accent color rather than inventing new visual language) so players can find and erase their own work if they hit `MAX_PLATFORMS_PER_PLAYER`~~ — *implemented and verified here, then **removed** in the room-wide ink redesign below: once the budget stopped being per-player, "find your own platforms to free up your quota" stopped being a meaningful affordance. `owner` survives on `PlatformData` as passive provenance metadata — it's just no longer rendered or quota-relevant*
- [x] Updated the on-screen hint text to mention right-click-to-erase
- [x] Manually verify: walls/ceiling contain the player within world bounds; right-click erases the targeted platform for everyone; erase respects rate limiting/validation and frees up the drawer's quota; erase persists across restarts; the highlight renders only for one's own platforms

> **Design discussion (with the user) before implementing:** endorsed **"anyone can erase anything"** — fits the "world is shaped by its players" theme from the GDD/CLAUDE.md (the trade-off is griefing potential, but it's easily reversible later to an owner-only check; `isValidErase`'s doc comment notes there's no owner check to *bypass*, since the permission model already allows it). Endorsed **right-click** as the standard, discoverable convention for "secondary action on an object." Chose to mark ownership via the **existing `#6ee7b7` accent color** (already meaning "(you)" elsewhere) rather than invent new visual language — and chose **closest-to-cursor** over z-order/topmost for hit-testing, since `Map` iteration order for `platforms` reflects each client's own arrival order (storage-listing order for late joiners vs. live-broadcast order for new draws) and is *not* globally consistent across clients, making "closest" both more robust and more intuitive.
>
> **Verified** end-to-end via a temporary `window.__debug` hook (extended this session with a generic `send` helper), synthetic `KeyboardEvent`/`MouseEvent` dispatch (driving real input-capture and drawing-capture code, including a genuine `contextmenu` right-click through `canvasPoint`'s coordinate scaling — mirroring the Phase 6 verification technique), and extra raw-`WebSocket` clients (the established multi-client technique from Phases 5–7):
> - **Walls/ceiling containment**: drove the player left for 10s — came to rest at `x≈15.64` (≈ `PLAYER_RADIUS=16`, the analytically-predicted left-wall boundary, `vx→0`); drove it right for 17.5s — came to rest at `x≈1584.36` (≈ `WORLD_WIDTH - PLAYER_RADIUS = 1584`, the right-wall boundary, `vx→0`). The ceiling uses the *exact same* body-construction call (`Matter.Bodies.rectangle({isStatic:true, label:"platform"})`) and the same label-based, geometry-based `isSupportingContact` check already proven correct for the ground and (now) both side walls — verified by code symmetry rather than a separate empirical climb-test, since a normal jump only rises ~96px (from `y≈844` to `y≈748`), nowhere near the `y≈16` ceiling; reaching it would require building and climbing a multi-platform staircase, disproportionate effort for code that's provably identical in mechanism to what's already empirically validated twice over.
> - **Right-click erase, the real user path**: drew a real freehand stroke via synthetic `mousedown`/`mousemove`/`mouseup` (mirroring actual drawing capture), then dispatched a genuine `contextmenu` `MouseEvent` at its midpoint — `defaultPrevented: true` confirmed `event.preventDefault()` suppressed the native menu, `findPlatformAt(canvasPoint(event))` correctly hit-tested the RDP-simplified stroke, and the resulting `erase` message round-tripped through the full pipeline: a fresh raw-`WebSocket` client's `world_state` showed **zero** platforms in the room afterward.
> - **Broadcast + "anyone can erase anything"**: a platform drawn by client A was erased by client B (a *different* connection/owner) — both the validation (no owner check) and the broadcast-to-everyone pattern were confirmed: client A's local `platforms` map and a third independent raw-`WebSocket` client both received `platform_removed` for the correct id.
> - **Rate limiting**: fired two erase requests back-to-back (<10ms apart, both for valid, existing platforms) — the first succeeded, the second (arriving within `ERASE_COOLDOWN_MS=250`) was silently dropped, leaving its target platform intact.
> - **Validation** (`isValidErase`): of 6 deliberately-malformed `erase` messages (missing `id`, non-string `id` as a number/`null`/array/object, wrong-cased `type: "ERASE"`), **all 6 were silently rejected** with the connection staying healthy throughout; a 7th message with a valid shape *plus* harmless extra keys (`points: [...]`) was correctly accepted and processed — confirming the type guard validates only what it documents (`type`+`id`) and intentionally tolerates extra payload, per its inline design comment.
> - **Quota freed on erase**: confirmed by code inspection that `ownedCount` (`handleDraw`, line 369) is computed by *dynamically filtering* `this.platforms.values()` by `owner` — and `handleErase` (line 401) deletes from that same `this.platforms` map, so the quota check naturally sees one fewer platform immediately after an erase, with no separate counter to fall out of sync.
> - **Persistence across restart**: erased four platforms (two via direct erase, one via cross-owner erase, one via the real right-click path), left one platform un-erased, then **fully restarted** the PartyKit dev server. A fresh raw-`WebSocket` client's `world_state` showed **exactly the one surviving platform, byte-for-byte identical** — and **none** of the four erased ones reappeared, proving `room.storage.delete` permanently removes the persisted record (not just the in-memory copy), symmetric to Phase 6's proof that `room.storage.put` persists it.
> - **Ownership highlight**: sampled canvas pixel data (`ctx.getImageData`) around a platform's rendered stroke — found **1244 pixels** matching the `#6ee7b7` halo color around the local player's own platform, and **0 matching pixels** around an identically-styled platform drawn by a different connection (which still rendered its own stroke color normally, just without the halo) — confirming `drawPlatformPath`'s `isOwn` branch (`platform.owner === conn.id`) renders correctly in both directions.
>
> **Bug found & fixed before verification (not during):** the `mousedown` listener didn't check `event.button`, so a right-click would *also* start a draw stroke (since `mousedown` fires for every mouse button) — directly conflicting with the new right-click-to-erase gesture. Fixed by adding `if (event.button !== 0) return;` so only the primary (left) button starts drawing.
>

## "Ink" budget — segment-based draw quota + visible meter

> Raised directly by the user, who found the old flat `MAX_PLATFORMS_PER_PLAYER=10` cap "limiting" and asked about performance implications of raising it. Discussion surfaced that a platform's *real* physics cost is its **segment** count (`createPlatformBodies` emits one body per consecutive point pair, so a maximally-long single stroke could cost ~70x what a single dot does under a flat per-platform cap) — so the user proposed basing the limit on total segments instead, and showing players how much "ink" they have left.

- [x] Server: replaced `MAX_PLATFORMS_PER_PLAYER=10` with `MAX_SEGMENTS_PER_PLAYER=200` — added `segmentCount(points)` (the same `points.length - 1` arithmetic `createPlatformBodies` uses, shared so the quota check and the "ink left" readout can't drift apart) and `ownedSegments(ownerId)` (derived fresh from `this.platforms` each call — the same single-source-of-truth approach `ownedCount` established for the erase feature's quota release, no separate counter to fall out of sync). `handleDraw`'s check became `ownedSegments + newSegments > MAX_SEGMENTS_PER_PLAYER` — a *cumulative budget*, not a per-draw cap
- [x] Server: added `sendInkUpdate(conn)` — broadcasts `{ type: "ink", used, max }` to one connection (`connection.send`, not `room.broadcast`, since it's player-specific); wired into `onConnect` (sends the `{used:0, max:200}` baseline right after `world_state`, so the UI never shows a placeholder), `handleDraw` (after every accepted draw), and `handleErase` (notifies the **erased platform's owner** via `this.room.getConnection(platform.owner)` — deliberately *not* the eraser, since this game's "anyone can erase anything" design means those can be different connections, and quota changes follow ownership)
- [x] Client: added an `#ink-meter` readout (built inside `startGame` alongside the chat panel — its content is meaningless before a room connection exists) showing `"Ink left: <remaining> / <max>"`, computed as `max - used` — pure display arithmetic on values the server already computed and sent directly, not a re-derivation of any server-side logic. Styled to match `#hint`/`.join-hint` (muted, small, `pointer-events: none`), positioned just above `#palette`
- [x] Client: added `isNumber` to the shape-check vocabulary (mirrors `isString`) and a `case "ink"` in the message switch validating `{used, max}` are both finite numbers
- [x] Manually verify: the meter shows the correct starting budget on join, decreases by exactly the drawn segment count after each accepted draw, increases when a platform is erased — including by a *different* player (proving the owner's live client gets updated regardless of who performed the erase) — and the quota correctly blocks (silently, with no stale `ink` broadcast) any draw that would push cumulative usage over the cap

> **Sizing rationale** (discussed inline with the user before implementing): `200` is roomier in the *typical* case — real RDP-simplified strokes run roughly 5-10 segments each (the Phase 6 verification note recorded a 21→8-point stroke, i.e. ~7 segments), so `200` reads as "20-40 strokes" vs. the old flat cap's "10 strokes regardless of length" — while *also tightening* the worst-case bound: the old scheme's de-facto ceiling was `MAX_PLATFORMS_PER_PLAYER x (MAX_DRAW_POINTS - 1)` = `10 x 499` ≈ 4990 segments per player, whereas the new scheme bounds total cost at exactly `200` regardless of how someone distributes it across strokes. `MAX_DRAW_POINTS=500` and `DRAW_COOLDOWN_MS=1000` are unchanged — they're orthogonal per-message-size and per-time-interval gates, not quota mechanisms.
>
> **Verified** end-to-end via `npx tsc --noEmit -p tsconfig.json` (clean, exit 0), driving the real join/draw UI through the preview tools (form-fill + `requestSubmit`, then synthetic `mousedown`/`mousemove`/`mouseup` dispatch through the real `canvasPoint`-scaled drawing-capture code — the established Phase 6 technique), and raw-`WebSocket` clients sending hand-built `draw`/`erase` messages with precisely-known segment counts (a new variant of the established multi-client technique, this time exploiting that `points.length - 1` is exactly predictable from a generated point array, to test the budget arithmetic to the exact integer):
> - **Baseline on join**: a freshly-joined connection's first `ink` message read `{used: 0, max: 200}`, and the meter immediately rendered `"Ink left: 200 / 200"` — no placeholder ever visible past the join transition.
> - **Draw decrements by the real segment count**: a synthetic freehand stroke produced a platform with `pointCount: 7` (confirmed via a fresh `world_state` listing, i.e. **6 segments** — `points.length - 1`), and the meter dropped to exactly `"Ink left: 194 / 200"` (200 − 6 = 194) — a precise, non-approximate match between the stored geometry and the displayed budget.
> - **Cross-player erase frees the owner's quota (the strongest test)**: a *second*, independently-identified connection (`Eraser`/`#c5a3f3`) erased that platform — proving "anyone can erase anything" still holds — and the *original owner's* (`Riley`, who didn't perform the erase) live meter immediately updated back to `"Ink left: 200 / 200"`, confirming `handleErase` correctly resolves and notifies the owner's connection via `room.getConnection`, independent of who triggered the removal.
> - **Exact cumulative-budget boundary test**: a fresh connection (`QuotaTester`, starting at `{used:0, max:200}`) sent three hand-built `draw`s of precisely-known segment counts spaced past `DRAW_COOLDOWN_MS`: **A** (49 segments) → accepted, `platform_added` confirmed 49 segments, `ink` updated to `{used: 49, max: 200}`; **B** (159 segments — cumulative would be `49 + 159 = 208 > 200`) → **silently rejected**: no `platform_added`, and critically **no `ink` broadcast at all** (proving a rejected draw leaves the budget, and what the client is told about it, completely untouched — not even a stale/incorrect update); **C** (99 segments — cumulative `49 + 99 = 148 ≤ 200`) → accepted, `platform_added` confirmed 99 segments, `ink` updated to exactly `{used: 148, max: 200}`. ## Ink budget redesign — room-wide quota + segment-level erase

> Follow-up to the "Ink budget" feature directly above, raised by the user almost as soon as it shipped. Two things felt off about the per-player design once it was in hand: (a) per-player tracking meant the *room* could still fill up with clutter even though no individual player looked over budget — the thing that actually bounds physics cost is total segments in the world, not any one person's share of them; and (b) whole-platform erase meant a single right-click could remove far more geometry than the click visually targeted (erasing one end of a long winding stroke deleted the whole thing). The user proposed making the budget room-wide *and* erase segment-precise — and the two changes turn out to depend on each other: a shared room-wide budget only feels fair if players can reclaim *exactly* the geometry they intend to remove, not whatever platform happens to contain it.

- [x] Server: renamed `MAX_SEGMENTS_PER_PLAYER` → `MAX_SEGMENTS_PER_ROOM`; replaced `ownedSegments(ownerId)` with a parameterless `totalSegments()` summing every platform in `this.platforms` (the same "derive fresh from the registry every time, never cache" pattern `ownedSegments`/`ownedCount` established) — `handleDraw`'s check became `totalSegments() + newSegments > MAX_SEGMENTS_PER_ROOM`, a budget shared by the whole room rather than divided per-player
- [x] Server: raised the cap from `200` to `MAX_SEGMENTS_PER_ROOM = 1200`, sized via a real empirical performance test against an isolated throwaway room — pushed it from 0 to ~9,800 segments across five checkpoints while sampling `snapshot`-broadcast timing: the tick stayed rock-solid (`mean ≈ 50ms`, the intended 20Hz) through ~3,920 segments, then fell off a cliff at ~5,586 (`mean ≈ 896ms`, `stddev ≈ 283ms` — almost 20x slower and wildly inconsistent) and stopped producing snapshots entirely beyond that. `1200` lands with roughly 3x headroom below the first sign of trouble — six times roomier than the old `200`, and now shared room-wide rather than multiplied by player count (which is what actually drives physics cost)
- [x] Server: replaced whole-platform erase with **segment-level** erase. `isValidEraseHit`/`isValidErase` now validate a *batch*: `{ type: "erase", hits: [{platformId, segmentIndex}, ...] }`, capped at `MAX_ERASE_HITS = 500` (same order of magnitude as `MAX_DRAW_POINTS`, for the same reason — legitimate drags, even fast ones crossing several overlapping platforms, land nowhere near it). `handleErase` groups hits by platform, fully removes each affected platform (bodies out of the live world, out of the registry, out of `room.storage`, `platform_removed` broadcast), then rebuilds 0-2 surviving sub-platforms via a new `splitPoints` helper — maximal contiguous runs of *non-removed* segments become fresh platforms with **brand-new random ids** but the **original owner and color carried through** (provenance survives a split; identity doesn't need to, since ids were never user-facing). Reuses the existing `platform_added`/`platform_removed` broadcast types — deliberately *not* a new `platform_split` message, since "one platform vanishes, 0-2 appear" is exactly what those two already express together
- [x] Server: `sendInkUpdate` dropped its per-connection-target design and became a no-arg `room.broadcast` — since the budget is room-wide, *everyone* needs to see the number change when *anyone* draws or erases (the same "broadcast to everyone, no special-cased local preview" pattern `platform_added`/`platform_removed` established, just applied to a different message type)
- [x] Client: replaced `findPlatformAt` (closest-*platform* hit-test) with `findSegmentAt` (closest-*segment* hit-test — same `pointToSegmentDistance`/`ERASE_HIT_TOLERANCE` machinery, finer-grained target). Right-click-drag now accumulates every unique segment crossed into a `Map<platformId, Set<segmentIndex>>` (`recordEraseHit`), and releasing the mouse (`finishErasing`) sends exactly **one** batched `erase` message — mirroring how `draw` already batches an entire stroke into a single message, which is also what lets the existing `ERASE_COOLDOWN_MS=250` keep working unchanged as a "once per gesture" gate rather than needing a new per-segment scheme
- [x] Client + server: removed the dashed ownership halo entirely — `OWN_PLATFORM_HIGHLIGHT`, the `isOwn` branch and parameter of `drawPlatformPath`, and the checklist line above describing it are all gone/struck through. `owner` stays on `PlatformData` (sanitized/validated/persisted/split exactly as before) as passive provenance metadata; it's just no longer rendered or quota-relevant
- [x] Updated the on-screen hint text: "Right-click a platform to erase it (yours are outlined)" → "Right-click and drag to erase"
- [x] Manually verify: the room-wide meter moves correctly regardless of *who* draws or erases; a multi-segment, multi-platform drag produces exactly one batched message; splitting yields the right surviving pieces with fresh ids and original owner/color; full removal (0 survivors) and interior splits (1-2 survivors) both work; the cooldown gates per-gesture, not per-segment; malformed/oversized batches are rejected; the halo is gone everywhere; persistence survives a restart

> **Design discussion (with the user) before implementing — five points, all explicitly agreed before writing code:** (1) make the quota room-wide (`MAX_SEGMENTS_PER_PLAYER` → `MAX_SEGMENTS_PER_ROOM`) and replace whole-platform erase with segment-level erase, since the two problems above are really one problem; (2) once ink is room-wide, per-player ownership stops being quota-relevant — remove the halo, but keep `owner` as inert metadata (costs nothing to retain, and a future moderation feature might want it); (3) batch a drag-erase into a single message exactly the way `draw` batches a stroke, so `ERASE_COOLDOWN_MS` keeps gating "once per gesture" with zero changes to its own logic; (4) reuse `platform_added`/`platform_removed` for splits rather than invent `platform_split` — the pair already says everything a split needs to say; (5) raise the segment cap, but back the new number with a real performance test rather than a guess.
>

## Cheese Race minigame + vote-to-start

> The first minigame loop: any player can propose one via chat, everyone present must agree, and the winning condition is simple enough to ship without round-reset machinery — "first to touch the cheese" needs no platform wipe, no scoring, no lobby state beyond "is a race active." Discussed and approved with the user as a full plan (vote infrastructure + Cheese Race + a *sketch-only* "Last Mouse Standing" survival-mode idea, deliberately deferred) before any code was written.

- [x] **Vote-to-start infrastructure**: typing `/race` in chat sends `minigame_propose`; [server/src/server.ts](server/src/server.ts) snapshots every connected player as an eligible voter (`PendingVote.voters`), auto-counts the proposer as "yes" (`pending = voters - proposer`), and broadcasts `minigame_vote_started`/`minigame_vote_progress` as `/yes`/`/no` (→ `minigame_vote`) come in. **Unanimity is required** — a single `/no` cancels immediately (`minigame_vote_resolved {outcome:"cancelled", reason:"no_vote", byUsername}`); all-yes resolves to `{outcome:"started"}` and calls `startCheeseRace()`. An unresolved vote auto-cancels after `VOTE_TIMEOUT_MS=60_000` — checked inside the existing 20Hz `step()` tick rather than a `setTimeout`, this codebase's established posture toward one-shot gameplay timers (its only timers are `onStart`'s periodic infrastructure intervals; reusing the tick sidesteps cancel-on-early-resolution bookkeeping entirely). Late joiners are spectators to an in-progress vote — silently ignored if they try to vote, matching the GDD's "drop invalid input silently" posture rather than erroring. `onClose` folds disconnects through the *same* `tryResolveVote()` that `handleMinigameVote` uses (so "what makes a vote resolve" is defined in exactly one place): a leaver is pruned from both `voters`/`pending`, and if the remaining pool drops below `MIN_PLAYERS_FOR_MINIGAME=2` the vote cancels outright (`reason:"left"`) — otherwise the shrunken pool can still complete the vote on its own.
- [x] **Cheese Race**: `startCheeseRace()` picks a uniformly random vertex of a uniformly random existing platform (`pickCheeseSpawn` — the same `Math.floor(Math.random() * arr.length)` idiom `pickUsername`/`generateRoomCode` already use, applied twice; RDP-simplified strokes already have vertices every few dozen pixels, so this reads as "a random point on the drawn world" without inventing segment-interpolation math), offset upward by `CHEESE_SURFACE_OFFSET = PLAYER_RADIUS + CHEESE_RADIUS + PLATFORM_THICKNESS/2` so it visually rests *on* the platform surface (generalizing Phase 6's empirically-verified "avatar rests on a platform surface, not at its raw `y`" math). An empty room (no platforms drawn yet) falls back to a fixed reachable point on the ground, `{x: WORLD_WIDTH/2, y: WORLD_HEIGHT - GROUND_THICKNESS - CHEESE_SURFACE_OFFSET}`. The win-check lives in `step()`, right after `Matter.Engine.update`, checking every player's *settled* position against `CHEESE_PICKUP_DISTANCE = PLAYER_RADIUS + CHEESE_RADIUS` (two circles "touch" exactly at the sum of their radii) — first toucher in `Map`-iteration (= arrival) order wins, an arbitrary but consistent tiebreak for the vanishingly-unlikely same-tick double-touch. On a win, `activeMinigame` clears and `minigame_ended {winnerId, winnerUsername}` broadcasts — platforms are deliberately **never wiped**; the race is a temporary ruleset overlay on the persistent world, not a round-reset system (and needed zero code to achieve — it's what *not* adding a wipe gives you for free).
- [x] **Race-mode drawing/erasing constraints** — the user's explicit design to keep races tense: while `activeMinigame` is set, `handleDraw` additionally rejects any stroke whose `points.length !== 2` (exactly one segment — layered as an *extra* check on top of `isValidDraw`'s general shape validation, not a parallel reimplementation of it) and `handleErase` truncates every batch to its first hit only (`data.hits.slice(0, 1)`, applied *before* the existing per-platform grouping — so the entire downstream grouping/splitting/broadcast logic stays untouched and naturally only ever sees one hit). Both gates also swap in their own cooldown identities, `RACE_DRAW_COOLDOWN_MS`/`RACE_ERASE_COOLDOWN_MS` (1000ms each — draw's matches the normal `DRAW_COOLDOWN_MS` numerically today but is named separately so "race mode has its own cooldown identity" stays grep-able without implying that equality is permanent; erase's is deliberately slower than the normal `ERASE_COOLDOWN_MS=250`, the user's explicit ask). [server/src/client.ts](server/src/client.ts) mirrors the draw cap live — `mousemove` calls a new `finalizeRaceStroke()` the *instant* `rdpSimplify` would introduce a second segment (mid-drag, not a bait-and-switch snap on release), sending just the first two points — and guards `recordEraseHit` to record at most one hit per gesture. Movement (`applyInput`) is deliberately left untouched; the user only asked to constrain drawing/erasing.
- [x] **UI**: a `#minigame-banner` (top-center, mirroring `#ink-meter`'s muted/`pointer-events:none` recipe) shows vote progress (`"<name> wants to play Cheese Race — N/M ready (type /yes or /no)"`) and race status (`"Cheese Race! First to the cheese wins"`); a `drawCheese()` free function renders a filled `CHEESE_RADIUS`-circle in `PALETTE_COLORS[2]` (`"#ffd479"` — already-palette "cheese yellow," no new color invented), wired into `frame()` between `drawPlatforms()`/`drawPlayers()`. `/race`/`/yes`/`/no` are recognized by a new `handleSlashCommand` in the chat input's Enter-handler — routed as their own typed, server-validated messages, *never* as chat text (keeping "chat is chat" and "votes are typed messages" cleanly separate, mirroring the server treating `isValidChat`/`isValidMinigameVote` as independent shapes). An unrecognized `/word` produces a **local-only** system note, never reaching the shared chat log. Vote/race milestones (`minigame_vote_started/_resolved`, `minigame_started/_ended`) all push through the existing `appendChatEntry`'s `"system"`-kind entries — the exact mechanism `player_joined`/`player_left` already use for "something notable happened, tell everyone," zero new notification surface. [server/public/index.html](server/public/index.html)'s `#hint` gained `· Type /race to vote on a minigame`.

## Client-side entity interpolation

> Players looked like they moved at a low frame rate — the server broadcasts position snapshots at 20Hz (`TICK_MS=50`) but the client renders at ~60fps, so each server position painted ~3 identical frames before snapping to the next. Picked up directly from the "Possible future features" idea sketched on 2026-06-07 (see below — that note's "ship interpolation for remote players only first, local prediction as a separate follow-up" leaning was superseded by a simpler call once actually planned: interpolate *all* avatars uniformly, local included, and accept the resulting ~100ms input-lag as the deliberate tradeoff — see `interpolation_plan.md`).

- [x] **Snapshot buffer + interpolation**: [server/src/client.ts](server/src/client.ts)'s module-level `latestPlayers` (the single newest snapshot, drawn as-is) became `snapshotBuffer: Snapshot[]` — a small history of `{receivedAt, players}` entries timestamped on arrival via `performance.now()`. Two mirrored constants were added: `SERVER_TICK_MS=50` (must stay in sync with the server's `TICK_MS`) and `INTERP_DELAY_MS = SERVER_TICK_MS * 2 = 100` — two snapshot intervals: one is the minimum buffer needed for there to normally be a "next" snapshot to tween toward, the second is jitter/dropped-packet margin. A new free function `playersAt(renderTime)` (per CLAUDE.md's "geometry stays data + free functions, never classes" convention) finds the two buffered snapshots bracketing `renderTime` and linearly interpolates each shared player's `x`/`y` between them — handling the edge cases explicitly: before the buffer's start (just connected) shows the oldest snapshot outright, past its end (server stall/dropped packets) *holds* the last known position rather than extrapolating (deliberately — holding is "still just rendering server data," extrapolation would cross into prediction), and players present in only one bracket (mid-join/-leave) draw at their last/first known spot until they age out naturally. `frame()` now calls `drawPlayers(playersAt(performance.now() - INTERP_DELAY_MS))` — rendering ~100ms in the past so there's (normally) always a bracket to interpolate within. The snapshot handler prunes the buffer to just what the current render window needs (`buf[0]` stays the one bracketing-older snapshot; everything before it is dropped) so it can't grow unbounded. This is a **client-only, render-only** change — no protocol changes, no server changes, and it deliberately respects "the client does no local physics or prediction": `playersAt` only ever blends between two real server-reported positions, never simulates one.
- [x] **Accepted tradeoff**: interpolating *all* avatars uniformly (not "remote players only," as the original future-features sketch leaned toward) means the local player's own avatar also renders ~100ms behind its actual server-side position — input lag that applies equally to everyone, a known and *accepted* cost of this approach (option #1 in `interpolation_plan.md`) chosen for its simplicity and zero risk of breaking the no-prediction convention. If this turns out to feel too laggy in practice, the documented follow-up is full client-side prediction (simulate locally, reconcile against server snapshots) — a meaningfully bigger lift that breaks the "client does no physics" rule and is explicitly *not* to be added preemptively.

> Verified via `npx tsc --noEmit` (clean before and after) and the live browser UI (`npm run dev`, synthetic `KeyboardEvent`/`MouseEvent` dispatch — the established technique): a temporary `CanvasRenderingContext2D.prototype.arc` monkey-patch (a new non-source-modifying variant of the project's "observe the client's own behavior without adding instrumentation to the source" technique, sampling every `ctx.arc(player.x, player.y, PLAYER_RADIUS, ...)` call — i.e. exactly the values `drawPlayers` paints each frame) recorded **170 consecutive frames of strictly-increasing, all-distinct `x` values** while holding a movement key (steady ~4.6px/frame ramp at a real ~16.7ms/frame cadence) — definitively the smooth tween the fix targets, not the old "3 identical frames then a ~14px jump" stair-step (confirmed absent: `maxIdenticalXWithinThatRun: 1` across the entire active-movement run; the only long identical-`x` runs in the full sample were during genuinely stationary periods, which is correct — interpolating between two equal positions yields that same position). Edge cases: a fresh join still fell and landed correctly (buffer-of-1 falls back to "draw the oldest/only snapshot"); a second raw-`WebSocket` client (`Brie`) joining and leaving mid-session produced correct `world_state`/`player_joined`/`player_left` handling with **no ghost avatar** left behind (screenshot-confirmed — only the local avatar remained, at its true post-movement position) and zero `console.warn` (confirming no protocol-shape drift through the unchanged `Array.isArray(msg.players)` check). No regressions: drawing a stroke, right-click-erasing it, and the live ink-meter readout (`1200 → 1198 → ...`) all rendered correctly through the same `frame()` loop, since interpolation only touches the `drawPlayers` call within it.

## Local-player prediction

> Direct follow-up to the interpolation feature directly above — its own "accepted tradeoff" note predicted this would be the natural next ask: making *all* avatars uniformly interpolated left the local player's own avatar lagging its keypresses by `INTERP_DELAY_MS` (~100ms), the dominant felt-latency complaint in a platformer where you're the one steering. Planned in `prediction_plan.md`, which stages the fix into four phases and stops "at the earliest phase that feels responsive enough."

- [x] **Phase 0 — shared simulation module** (prerequisite, shipped as a structural deviation from the plan's single-file suggestion): split into [server/src/physics.ts](server/src/physics.ts) (pure constants, `Point`/`Keys` types, `isSupportingContact` — `import type * as Matter` only, erased at compile time) and [server/src/physics-bodies.ts](server/src/physics-bodies.ts) (`createPlatformBodies`/`applyMovement`/`createPlayerBody`/`createBoundaryBodies` — real `import Matter from "matter-js"`). The split exists because of an empirical mid-session discovery: a *value* import of anything from a module that itself does `import Matter from "matter-js"` (a CommonJS `require`) can't be tree-shaken — the whole ~84KB-minified runtime rides along regardless of what's actually used. A bundle importing only `physics.ts` measured 320 bytes / zero `matter-js` references; the moment a body factory entered the graph, the full runtime did too. `server.ts` and `client.ts` now both import shared constants/types/the ground-contact predicate from `physics.ts` (replacing the client's old hand-mirrored copies); `server.ts` additionally imports the body factories (it always paid the Matter cost — it's the authority). Verified behavior-preserving via a temporary `verify-phase0-split-tmp.mjs` raw-WebSocket script (deleted after use): sampled `y≈844.36`/`vy≈-9.85` matched pre-refactor documented values exactly.
- [x] **Phase 1 — horizontal-only prediction** (shipped): [server/src/client.ts](server/src/client.ts) gained `predictLocalX(dtMs)`, integrating the local avatar's held `keys` directly each frame (`dir * MOVE_SPEED * (dtMs / TICK_MS)`, clamped to the world's side walls) — a faithful, Matter-free rebuild of the server's direct-velocity horizontal model, requiring no physics engine client-side. `keys` moved from `startGame`-local to module-level (mirroring `conn`) so the module-level `predictLocalX`/`frame` can read it. The `"snapshot"` handler now reconciles: eases `localX` toward the authoritative `me.x` by `RECONCILE_BLEND=0.15` per snapshot, or hard-snaps if `|error| > PREDICT_SNAP_PX=64` (large errors signal a real discontinuity — teleport/reconnect/knockback — not jitter; easing through one would just look like floating). `frame()` substitutes `localX` for the local player's `x` only (`y` stays interpolated — the documented Phase 1 limitation: jumps/falls lag slightly behind input) by building a *fresh* array via `.map()`, **not** the in-place `me.x = localX` mutation the plan's pseudocode sketched — `playersAt`'s edge-case branches return snapshot objects by reference from `snapshotBuffer`, so in-place mutation would have permanently corrupted buffered interpolation/reconciliation data. A real bug in the plan's own sketch, caught and fixed during implementation.
- [x] **Convention exceptions recorded in CLAUDE.md** (both required by the plan, both now also pinned as bullets in "Conventions established so far"): (1) local prediction is a deliberate, narrowly-scoped exception to "the client does no local physics or prediction" — only the local avatar's `x`, continuously corrected by server snapshots, remote players untouched, server still sole authority; (2) the movement model is now single-sourced in `physics.ts`/`physics-bodies.ts` rather than hand-mirrored, since faithful prediction requires running the server's *exact* model and a hand-copy only guarantees drift.
- [ ] **Phase 2 — full local physics sim** (not started, available if needed): run a real local Matter.js world for the local player only, predicting jumps/falls/collisions too. Bundles Matter into the client (~tens of KB). Only worth doing if Phase 1's vertical-motion lag feels bothersome in practice.
- [ ] **Phase 3 — input sequence numbers + reconciliation replay** (not started, available if needed): tag `input` messages with `seq`, have the server echo back `lastInput`, replay unacknowledged inputs after each correction. Eliminates the standing reconciliation error entirely; a small protocol addition, optional precision upgrade on top of either Phase 1 or 2.

> **Stopped at Phase 1**, per the plan's own explicit guidance ("stop at the earliest phase that feels responsive enough — don't build later phases preemptively"): testing showed a ~28ms input-to-movement latency (down from ~100ms) and smooth, gentle reconciliation, which felt responsive enough to not warrant Phase 2/3's added complexity right now. **Accepted limitation** (the plan's own documented "honest limitation," confirmed rather than eliminated): because reconciliation eases toward a snapshot that's already ~RTT+tick old, there's a small standing error while continuously running that the blend constantly chases — invisible on localhost/low latency, potentially feeling slightly floaty under high latency. Phase 3 (replay) is the documented fix if that ever becomes bothersome.
>

A second raw-WebSocket client (`verify-prediction-remote-tmp.mjs`, "Remote"/`#a3c4f3`, deleted after use) confirmed remote-player rendering is completely unaffected: correct identity/color, smooth interpolation, no ghost avatar after disconnect. No regressions: jumping (still pure-interpolated `y`) rose ~110px exactly as before; drawing/ink-meter worked through the same `frame()` loop (`1200→1199`). Zero `console.warn` throughout. **One gap deliberately left untested and disclosed rather than silently skipped:** the `PREDICT_SNAP_PX=64` hard-snap branch was never exercised with an artificially-large injected desync (would need source edits or real message-injection machinery — disproportionate given `tsc` is clean, the structurally-identical "ease" branch was empirically proven correct 56 times over, and the snap branch is a single trivially-correct conditional assignment).
