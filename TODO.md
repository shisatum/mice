# Build Checklist

Chronological checklist mirroring the GDD's "Recommended Build Order" ([gdd_partykit.md](gdd_partykit.md)).

**How to use this file:**
- Check it at the start of every session to see where things stand.
- Check items off (`[x]`) as you complete them.
- Phases are expanded into sub-tasks only once you start them — expand the next phase's checkbox into concrete sub-tasks when you begin it, since detailed planning too far ahead tends to drift from reality.

---

## Phase 1 — Single-player prototype

> Canvas + Matter.js, no networking. Validates the core fun: drawing → physics body → mouse avatar can jump on it.

- [x] Set up `prototype/index.html` — single self-contained file, Matter.js via CDN (`matter-js@0.20.0`), no build step
- [x] Drawing capture: mousedown/mousemove/mouseup → freehand path as `{x, y}[]`
- [x] Path → physics body: chain of thin static rectangle segments along the drawn path
- [x] Avatar body: circle with locked rotation (`inertia: Infinity`) so it slides instead of rolling
- [x] Controls: arrow keys / WASD → horizontal velocity + one-shot jump velocity
- [x] Ground detection: `collisionStart`/`collisionEnd` → `groundContacts` counter → `grounded` flag (gates jumping)
- [x] Render loop: custom `requestAnimationFrame`, draw platforms from their point arrays + avatar as a circle (not `Matter.Render`)
- [x] Manually verify: draw platforms of various shapes, confirm avatar runs/jumps on them without falling through or infinite-air-jumping

> **Verified** (via automated browser testing — drawing simulated mouse paths, sampling physics state every frame): the avatar climbs hand-drawn slopes, stands on elevated drawn platforms, falls off edges, and jumps with a clean ~167px arc. `grounded` correctly gates jumping (no infinite air-jumps).
>
> **Bug found & fixed during verification:** the initial `isSupportingContact` check only tested whether the contact normal was vertical, not which side the platform was on — so bumping your head on a platform's underside mid-jump could be miscounted as "landing," refreshing the jump at the worst moment. Fixed by checking the normal's sign relative to which body is the player (Matter 0.20's SAT normal is not a simple "bodyA → bodyB" center-to-center vector — the correct sign convention was derived empirically and is documented inline in `isSupportingContact`).

## Phase 3 — Server-authoritative physics loop

- [x] Port a minimal physics setup (engine, gravity, static ground) into [server/src/server.ts](server/src/server.ts), running on a `setInterval` tick at ~20Hz
- [x] `onStart`: create the Matter.js engine/world + ground; `onConnect`: add a player body to the world (mirroring the prototype's circle avatar with locked rotation); `onClose`: remove it
- [x] Broadcast `snapshot` messages (`{ type: "snapshot", players: [{id,x,y,vx,vy}], tick }`) each tick via `this.room.broadcast`
- [x] Build a minimal client ([server/src/client.ts](server/src/client.ts) + canvas in `public/index.html`) that connects, receives snapshots, and renders player position(s) — no input/controls yet, purely observing server-driven movement

> **Verified** by sampling 120 snapshot broadcasts via a temporary `window.__debug` hook (same pattern as Phase 1): the player spawned at `y≈251.66` falling (`vy≈0.83`), and within ~30 ticks settled at `y≈844.36` with `vy=0` — exactly the calculated resting position on the ground (ground top at `y=860`, minus the player's 16px radius). 120 samples spanning ticks 2682–2801 confirmed a steady ~20Hz broadcast. Confirmed server-authoritative (not a static render) since the position genuinely changes tick-over-tick driven purely by the room's Matter.js simulation. Debug hook fully removed afterward (verified via Grep — 0 matches for `__debug|TEMP DEBUG`).
>
> **Bug found & fixed during setup:** the GDD's own example code calls `Matter.Engine.update(engine, 50)` directly at the 20Hz tick rate, but Matter.js warns that delta arguments above ~16.667ms risk instability/tunneling through thin bodies (which matters a lot once Phase 6 introduces thin drawn-platform segments). Fixed by sub-stepping the engine at a fixed ~60Hz internally (3 sub-steps of `1000/60`ms per 50ms tick) while still broadcasting snapshots at 20Hz — confirmed the warning no longer appears on a clean server run.
>
> Added a `server-dev` entry to [.claude/launch.json](.claude/launch.json) (backed by `server/dev.cmd`, since the Node.js install directory isn't on the preview tool's spawn `PATH` — the wrapper script prepends it) so the PartyKit dev server can be driven through the browser-preview tooling like the prototype.

## Phase 4 — Player input pipeline

- [x] Client sends `input` messages (`{ left, right, jump }`); server applies them to the player's body
- [x] Server tracks per-connection key state (`{ left, right, jump }`) and applies the same movement logic the prototype used (direct velocity, one-shot gated jump) to that connection's body each tick — see `applyInput` in [server/src/server.ts](server/src/server.ts)
- [x] Client adds keyboard capture (arrow keys / WASD, up/W/Space to jump) and sends `input` messages on change — render loop stays snapshot-driven (no client-side prediction yet); added an on-screen control hint
- [x] Manually verify: moving/jumping the local player is visible in the canvas, server-authoritatively, with correct ground-gating (reusing the prototype's empirically-derived `isSupportingContact` sign convention)

> **Verified** end-to-end via a temporary `window.__debug` hook sampling snapshot broadcasts while programmatically driving `setKey`:
> - **Horizontal movement**: resting `{x:800, vx:0}` → after holding right ~1s, `{x:1082.2, vx:4.26}` (accelerating toward `MOVE_SPEED=5` under `frictionAir`) → on release, `{x:1082.2, vx:0}`. Proves the full round trip: keypress → `input` message → server validation → per-connection key state → `applyInput` → `Matter.Body.setVelocity` → physics → broadcast → client render.
> - **Jump + mid-air gating**: grounded `{vy:0, y:844.36}` → jump impulse peaks at `vy≈-9.85` (≈ `-JUMP_SPEED=11` reduced by one tick of gravity/sub-stepping before the snapshot is taken) → rises and decelerates under gravity (`vy:-5.57` → `vy:-0.91` near apex) → a second jump press while still airborne produced **no** fresh `-11` impulse (correctly gated, continued its existing arc) → lands back at `{vy:0, y:844.36}`.
> - **Re-arming after landing**: immediately after landing, a fresh jump press peaked at `vy≈-9.85` again — identical to the first jump — proving `groundContacts`/`jumpHeld` correctly re-arm the one-shot jump once grounded again.
>
> Debug hook fully removed afterward (verified via Grep — 0 matches for `__debug|TEMP DEBUG`).
>
> **False alarm caught during verification:** an early test run showed the player frozen mid-test (`landed`/`secondJump`/`landedAgain` samples all identical, ticks barely advancing despite seconds of elapsed time). Root cause was the *test harness*, not the game: the `dbg.samples` ring buffer was capped at 400 entries and had filled up across back-to-back `preview_eval` runs, so `latestFor` kept returning the last-recorded (stale) sample instead of fresh data. Re-running with `dbg.samples.length = 0` resets between phases produced clean, consistent results — no bug in `applyInput`/ground-detection.

- [x] Server broadcasts `platform_added` to *everyone including the drawer* (`{ type: "platform_added", id, points, color, owner }`) — same "no special-cased local preview" pattern as Phase 5's `player_joined`; `world_state` now also includes existing platforms for late joiners

## Walls & erase feature

> Two community-facing additions picked up after the GitHub repo went public: world boundaries (so players can't run/fall off the edge of the world into the void) and a shared erase tool (so the canvas doesn't fill up with permanent clutter — fits the "world is shaped by its players" theme).

- [x] Server: add static `leftWall`/`rightWall`/`ceiling` bodies (alongside the existing ground) bounding the `WORLD_WIDTH x WORLD_HEIGHT` play space — all sharing `label: "platform"` so the existing `isSupportingContact` collision logic (empirically derived in Phase 1, unchanged since) handles them uniformly with zero special-casing
- [x] Server: `erase` message validation (`isValidErase`) + `handleErase` — removes the platform's bodies from the live Matter.js world, drops it from the registry, deletes its persisted `room.storage` record, and broadcasts `platform_removed` to everyone (including the eraser — same "no special-cased local preview" pattern as `draw`/`platform_added`); rate-limited via `ERASE_COOLDOWN_MS=250` (looser than `DRAW_COOLDOWN_MS=1000`, since erasing doesn't strain physics — purely a storage/broadcast-spam guard, not a gameplay gate)
- [x] Client: right-click capture (`contextmenu`, with `event.preventDefault()` to suppress the native browser menu) + closest-platform hit-testing (`findPlatformAt`, using a new `pointToSegmentDistance` helper — distance to a finite *segment*, vs. the existing `perpendicularDistance`'s distance to an infinite *line* used only for RDP simplification — within `ERASE_HIT_TOLERANCE = PLATFORM_THICKNESS/2 + 6`)
- [x] Client: highlight the local player's own platforms with a dashed halo (`OWN_PLATFORM_HIGHLIGHT = "#6ee7b7"`, reusing the existing "(you)" accent color rather than inventing new visual language) so players can find and erase their own work if they hit `MAX_PLATFORMS_PER_PLAYER`
- [x] Updated the on-screen hint text to mention right-click-to-erase
- [x] Manually verify: walls/ceiling contain the player within world bounds; right-click erases the targeted platform for everyone; erase respects rate limiting/validation and frees up the drawer's quota; erase persists across restarts; the highlight renders only for one's own platforms

> **Design discussion (with the user) before implementing:** endorsed **"anyone can erase anything"** — fits the "world is shaped by its players" theme from the GDD/CLAUDE.md (the trade-off is griefing potential, but it's easily reversible later to an owner-only check; `isValidErase`'s doc comment notes there's no owner check to *bypass*, since the permission model already allows it). Endorsed **right-click** as the standard, discoverable convention for "secondary action on an object." Chose to mark ownership via the **existing `#6ee7b7` accent color** (already meaning "(you)" elsewhere) rather than invent new visual language — and chose **closest-to-cursor** over z-order/topmost for hit-testing, since `Map` iteration order for `platforms` reflects each client's own arrival order (storage-listing order for late joiners vs. live-broadcast order for new draws) and is *not* globally consistent across clients, making "closest" both more robust and more intuitive.
>
> **Verified** end-to-end via a temporary `window.__debug` hook (extended this session with a generic `send` helper), synthetic `KeyboardEvent`/`MouseEvent` dispatch (driving real input-capture and drawing-capture code, including a genuine `contextmenu` right-click through `canvasPoint`'s coordinate scaling — mirroring the Phase 6 verification technique), and extra raw-`WebSocket` clients (the established multi-client technique from Phases 5–7):
> - **Walls/ceiling containment**: drove the player left for 10s — came to rest at `x≈15.64` (≈ `PLAYER_RADIUS=16`, the analytically-predicted left-wall boundary, `vx→0`); drove it right for 17.5s — came to rest at `x≈1584.36` (≈ `WORLD_WIDTH - PLAYER_RADIUS = 1584`, the right-wall boundary, `vx→0`). The ceiling uses the *exact same* body-construction call (`Matter.Bodies.rectangle({isStatic:true, label:"platform"})`) and the same label-based, geometry-based `isSupportingContact` check already proven correct for the ground and (now) both side walls — verified by code symmetry rather than a separate empirical climb-test, since a normal jump only rises ~96px (from `y≈844` to `y≈748`), nowhere near the `y≈16` ceiling; reaching it would require building and climbing a multi-platform staircase, disproportionate effort for code that's provably identical in mechanism to what's already empirically validated twice over.
> - **Right-click erase, the real user path**: drew a real freehand stroke via synthetic `mousedown`/`mousemove`/`mouseup` (mirroring actual drawing capture), then dispatched a genuine `contextmenu` `MouseEvent` at its midpoint — `defaultPrevented: true` confirmed `event.preventDefault()` suppressed the native menu, `findPlatformAt(canvasPoint(event))` correctly hit-tested the RDP-simplified stroke, and the resulting `erase` message round-tripped through the full pipeline: a fresh raw-`WebSocket` client's `world_state` showed **zero** platforms in the room afterward.
> - **Broadcast + "anyone can erase anything"**: a platform drawn by client A was erased by client B (a *different* connection/owner) — both the validation (no owner check) and the broadcast-to-everyone pattern were confirmed: client A's local `platforms` map and a third independent raw-`WebSocket` client both received `platform_removed` for the correct id.
> - **Rate limiting**: fired two erase requests back-to-back (<10ms apart, both for valid, existing platforms) — the first succeeded, the second (arriving within `ERASE_COOLDOWN_MS=250`) was silently dropped, leaving its target platform intact.
> - **Validation** (`isValidErase`): of 6 deliberately-malformed `erase` messages (missing `id`, non-string `id` as a number/`null`/array/object, wrong-cased `type: "ERASE"`), **all 6 were silently rejected** with the connection staying healthy throughout; a 7th message with a valid shape *plus* harmless extra keys (`points: [...]`) was correctly accepted and processed — confirming the type guard validates only what it documents (`type`+`id`) and intentionally tolerates extra payload, per its inline design comment.
> - **Quota freed on erase**: confirmed by code inspection that `ownedCount` (`handleDraw`, line 369) is computed by *dynamically filtering* `this.platforms.values()` by `owner` — and `handleErase` (line 401) deletes from that same `this.platforms` map, so the quota check naturally sees one fewer platform immediately after an erase, with no separate counter to fall out of sync.
> - **Persistence across restart**: erased four platforms (two via direct erase, one via cross-owner erase, one via the real right-click path), left one platform un-erased, then **fully restarted** the PartyKit dev server. A fresh raw-`WebSocket` client's `world_state` showed **exactly the one surviving platform, byte-for-byte identical** — and **none** of the four erased ones reappeared, proving `room.storage.delete` permanently removes the persisted record (not just the in-memory copy), symmetric to Phase 6's proof that `room.storage.put` persists it.
> - **Ownership highlight**: sampled canvas pixel data (`ctx.getImageData`) around a platform's rendered stroke — found **1244 pixels** matching the `#6ee7b7` halo color around the local player's own platform, and **0 matching pixels** around an identically-styled platform drawn by a different connection (which still rendered its own stroke color normally, just without the halo) — confirming `drawPlatformPath`'s `isOwn` branch (`platform.owner === conn.id`) renders correctly in both directions.
>
> **Bug found & fixed before verification (not during):** the `mousedown` listener didn't check `event.button`, so a right-click would *also* start a draw stroke (since `mousedown` fires for every mouse button) — directly conflicting with the new right-click-to-erase gesture. Fixed by adding `if (event.button !== 0) return;` so only the primary (left) button starts drawing.
>
> Debug hook (including the `send` helper added this session) fully removed afterward (verified via Grep — 0 matches for `__debug|TEMP DEBUG`); `npx tsc --noEmit -p tsconfig.json` clean both before and after removal.

## Chat feature

> Toggleable chat (Enter to open/close), so players can coordinate without leaving the canvas — also doubles as a join/leave activity log (usernames only, never IPs/connection ids), reusing the same broadcast/sanitization/rate-limit patterns `draw`/`erase` established.

- [x] Server: `chat` message validation (`isValidChat`) + `handleChat` — sanitizes text (`sanitizeChatText`, reusing `CONTROL_CHARS`, capped at `MAX_CHAT_LENGTH=240`), rate-limited via `CHAT_COOLDOWN_MS=400` (per-connection `lastChatAt` map, mirroring `lastDrawAt`/`lastEraseAt`), reads `username`/`color` from the connection's own server-tracked `PlayerState` (never trusts client-supplied identity — only `text` comes from the message), and broadcasts `{ type: "chat", id, username, color, text }` to everyone including the sender (same "no special-cased local preview" pattern as `draw`/`erase`)
- [x] Client: a collapsed "ticker" pinned bottom-left (clipped via flexbox to show only the latest lines, `pointer-events: none` so it never blocks drawing beneath it) that expands into an opaque, scrollable panel + input box on Enter (`setChatOpen`/`#chat.expanded`); Escape cancels and closes; Enter while open sends and closes
- [x] Client: derives system log entries (`"<username> joined"`/`"<username> left"`) purely from the existing `player_joined`/`player_left` broadcasts — no new protocol surface needed, and critically exposes only usernames, never connection ids or IP addresses (the roster is looked up *before* `roster.delete()` runs on `player_left`, so the leaving player's name is still available)
- [x] Client: suppress movement-key capture while the chat input has focus (`chatOpen` guard added to `setKey`, plus `event.stopPropagation()` on the input's own `keydown` so keystrokes never reach the `window`-level handlers at all), and proactively zero-and-resend `{left,right,jump}` on open so a held movement key can't get stuck mid-motion when its `keyup` would otherwise be swallowed
- [x] Updated the on-screen hint text to mention "Press Enter to chat"
- [x] Manually verify: Enter toggles the panel; messages broadcast and render with correct username/color (including cross-client); join/leave produce system log entries with usernames only (never ids/IPs); movement is suppressed while chat is open (and a held key gets corrected on open); rate limiting and the length cap hold; console stays warning-free

> **Verified** end-to-end via `npx tsc --noEmit -p tsconfig.json` (clean, exit 0, both before and after), synthetic `keydown`/focus-event dispatch driving the real chat-toggle/send code, a temporary `WebSocket.prototype.send` monkey-patch (a new variant of the project's established "raw WebSocket" verification technique — this one intercepts the *local* client's own outgoing frames in-page, without modifying source, to prove what it does and doesn't send), and a second raw-`WebSocket` client joining the same room (`B2J7VL`) with an independent identity (`Brie` / `#f6a5c0` — the established multi-client technique from Phases 5–7):
> - **Toggle + send/cancel**: Enter opened the panel (`.expanded` class added, input focused); typing "hello world, this is a test message" and pressing Enter sent it, rendered it as `"Riley: hello world, this is a test message"` with the username colored `rgb(143, 211, 182)` (= `#8fd3b6`, Riley's *own* chosen avatar color — proving the server reads identity from `PlayerState`, not anything the message carries), and auto-closed the panel; Escape cancelled a half-typed message, cleared the input, and closed without sending.
> - **Movement suppression + stuck-key correction**: the monkey-patched `send` confirmed **zero** `input` frames went out while typing WASD letters into the chat box (the `chatOpen` guard + `stopPropagation` fully isolate it from the window-level handlers), and that opening the panel while `ArrowRight` was held immediately fired exactly one corrective frame — `{"type":"input","keys":{"left":false,"right":false,"jump":false}}` — proving a movement key can't get stuck mid-motion when its `keyup` would otherwise never arrive.
> - **Rate limiting**: two messages sent <1ms apart — the first (`"rapid-1"`) landed, the second (`"rapid-2"`) was silently dropped (only 3 chat entries existed at that check: "Riley joined", the test message, and "rapid-1"); a whitespace-only message was never even sent (caught client-side by `.trim()`, which produces an empty string before anything reaches the wire).
> - **Length cap**: a 400-character message came back truncated to exactly **`MAX_CHAT_LENGTH=240`** characters — confirmed by counting the rendered `"Riley: yyyy...y"` entry's `'y'` characters: 241 total = 240 message chars + 1 from "Riley".
> - **Cross-client join/leave + chat (the strongest test)**: a second raw-`WebSocket` client (`Brie`, `#f6a5c0`) joined room `B2J7VL`, sent `{type:"chat", text:"hi from Brie"}`, then disconnected. Riley's log showed, in order: `"Riley joined"` → (Riley's own test messages) → **`"Brie joined"`** → **`"Brie: hi from Brie"`**, rendered with username color `rgb(246, 165, 192)` (= `#f6a5c0` — *Brie's* color, not Riley's, proving per-sender identity is read fresh from each connection's own `PlayerState`) → **`"Brie left"`**. No connection ids or IP addresses appear anywhere in the log — only usernames, exactly per the requirement.
> - **Console hygiene**: zero `console.warn`/`console.error` output throughout — every `chat` broadcast matched the client's minimal shape-check (`isString` on `id`/`username`/`color`/`text`) with no protocol drift, per the "trust the shape, log what doesn't fit" posture pinned in CLAUDE.md.

## "Ink" budget — segment-based draw quota + visible meter

> Raised directly by the user, who found the old flat `MAX_PLATFORMS_PER_PLAYER=10` cap "limiting" and asked about performance implications of raising it. Discussion surfaced that a platform's *real* physics cost is its **segment** count (`createPlatformBodies` emits one body per consecutive point pair, so a maximally-long single stroke could cost ~70x what a single dot does under a flat per-platform cap) — so the user proposed basing the limit on total segments instead, and showing players how much "ink" they have left.

- [x] Server: replaced `MAX_PLATFORMS_PER_PLAYER=10` with `MAX_SEGMENTS_PER_PLAYER=200` — added `segmentCount(points)` (the same `points.length - 1` arithmetic `createPlatformBodies` uses, shared so the quota check and the "ink left" readout can't drift apart) and `ownedSegments(ownerId)` (derived fresh from `this.platforms` each call — the same single-source-of-truth approach `ownedCount` established for the erase feature's quota release, no separate counter to fall out of sync). `handleDraw`'s check became `ownedSegments + newSegments > MAX_SEGMENTS_PER_PLAYER` — a *cumulative budget*, not a per-draw cap
- [x] Server: added `sendInkUpdate(conn)` — broadcasts `{ type: "ink", used, max }` to one connection (`connection.send`, not `room.broadcast`, since it's player-specific); wired into `onConnect` (sends the `{used:0, max:200}` baseline right after `world_state`, so the UI never shows a placeholder), `handleDraw` (after every accepted draw), and `handleErase` (notifies the **erased platform's owner** via `this.room.getConnection(platform.owner)` — deliberately *not* the eraser, since this game's "anyone can erase anything" design means those can be different connections, and quota changes follow ownership)
- [x] Client: added an `#ink-meter` readout (built inside `startGame` alongside the chat panel — its content is meaningless before a room connection exists) showing `"Ink left: <remaining> / <max>"`, computed as `max - used` — pure display arithmetic on values the server already computed and sent directly, not a re-derivation of any server-side logic. Styled to match `#hint`/`.join-hint` (muted, small, `pointer-events: none`), positioned just above `#palette`
- [x] Client: added `isNumber` to the shape-check vocabulary (mirrors `isString`) and a `case "ink"` in the message switch validating `{used, max}` are both finite numbers
- [x] Manually verify: the meter shows the correct starting budget on join, decreases by exactly the drawn segment count after each accepted draw, increases when a platform is erased — including by a *different* player (proving the owner's live client gets updated regardless of who performed the erase) — and the quota correctly blocks (silently, with no stale `ink` broadcast) any draw that would push cumulative usage over the cap

> **Sizing rationale** (discussed inline with the user before implementing): `200` is roomier in the *typical* case — real RDP-simplified strokes run roughly 5-10 segments each (the Phase 6 verification note recorded a 21→8-point stroke, i.e. ~7 segments), so `200` reads as "20-40 strokes" vs. the old flat cap's "10 strokes regardless of length" — while *also tightening* the worst-case bound: the old scheme's de-facto ceiling was `MAX_PLATFORMS_PER_PLAYER x (MAX_DRAW_POINTS - 1)` = `10 x 499` ≈ 4990 segments per player, whereas the new scheme bounds total cost at exactly `200` regardless of how someone distributes it across strokes. `MAX_DRAW_POINTS=500` and `DRAW_COOLDOWN_MS=1000` are unchanged — they're orthogonal per-message-size and per-time-interval gates, not quota mechanisms.
>
> **Verified** end-to-end via `npx tsc --noEmit -p tsconfig.json` (clean, exit 0), driving the real join/draw UI through the preview tools (form-fill + `requestSubmit`, then synthetic `mousedown`/`mousemove`/`mouseup` dispatch through the real `canvasPoint`-scaled drawing-capture code — the established Phase 6 technique), and raw-`WebSocket` clients sending hand-built `draw`/`erase` messages with precisely-known segment counts (a new variant of the established multi-client technique, this time exploiting that `points.length - 1` is exactly predictable from a generated point array, to test the budget arithmetic to the exact integer):
> - **Baseline on join**: a freshly-joined connection's first `ink` message read `{used: 0, max: 200}`, and the meter immediately rendered `"Ink left: 200 / 200"` — no placeholder ever visible past the join transition.
> - **Draw decrements by the real segment count**: a synthetic freehand stroke produced a platform with `pointCount: 7` (confirmed via a fresh `world_state` listing, i.e. **6 segments** — `points.length - 1`), and the meter dropped to exactly `"Ink left: 194 / 200"` (200 − 6 = 194) — a precise, non-approximate match between the stored geometry and the displayed budget.
> - **Cross-player erase frees the owner's quota (the strongest test)**: a *second*, independently-identified connection (`Eraser`/`#c5a3f3`) erased that platform — proving "anyone can erase anything" still holds — and the *original owner's* (`Riley`, who didn't perform the erase) live meter immediately updated back to `"Ink left: 200 / 200"`, confirming `handleErase` correctly resolves and notifies the owner's connection via `room.getConnection`, independent of who triggered the removal.
> - **Exact cumulative-budget boundary test**: a fresh connection (`QuotaTester`, starting at `{used:0, max:200}`) sent three hand-built `draw`s of precisely-known segment counts spaced past `DRAW_COOLDOWN_MS`: **A** (49 segments) → accepted, `platform_added` confirmed 49 segments, `ink` updated to `{used: 49, max: 200}`; **B** (159 segments — cumulative would be `49 + 159 = 208 > 200`) → **silently rejected**: no `platform_added`, and critically **no `ink` broadcast at all** (proving a rejected draw leaves the budget, and what the client is told about it, completely untouched — not even a stale/incorrect update); **C** (99 segments — cumulative `49 + 99 = 148 ≤ 200`) → accepted, `platform_added` confirmed 99 segments, `ink` updated to exactly `{used: 148, max: 200}`. Every number matched its prediction exactly — proving the check is a genuine *cumulative* budget (`ownedSegments + newSegments > max`), not a flat per-draw or per-platform limit, and that crossing the line produces a clean, silent rejection consistent with this project's "drop invalid/over-limit input silently" security posture (gdd_partykit.md).
> - **Console hygiene**: zero `console.warn`/`console.error` throughout — every `ink` message matched the client's minimal shape-check (`isNumber` on `used`/`max`) with no protocol drift.

## Possible future features (not started — ideas only)

> Raised in discussion on 2026-06-07; deliberately not scheduled yet. Notes below capture the thinking so a future session doesn't have to re-derive it.

- [ ] **Server/room list on the join screen** — let players see active games instead of only "enter a code." PartyKit has no built-in room-enumeration API (rooms are created lazily on first connection, and there's no client-facing "list all rooms" call), so a literal public lobby browser would need extra infrastructure. Cheapest-to-priciest options discussed:
  - *Cheap*: a `localStorage`-backed "recent rooms" list on the join screen — remember room codes you've joined before and offer one-click rejoin. Pure client-side, zero server changes, solves the most common case.
  - *Medium*: a singleton "directory" room that active game rooms register/ping on `onStart` (or periodically), which the join screen queries for `{roomId, playerCount}` — a real feature (new room class + registration protocol + staleness/cleanup), but doable.
  - Related but smaller: a clearer "create vs. join" distinction in the UI (right now both are "enter a code") — cheap, pure client-side, arguably bigger UX win than a list.
  - Leaning: ship the `localStorage` version first; treat a real directory as its own follow-up project if wanted.
- [ ] **Client-side interpolation ("lerping") for smoother movement** — the client currently renders raw ~20Hz snapshot positions, so remote avatars will look steppy between ticks (most visible on other players, since there's no local input to mask it for them). Standard fix: render remote avatars interpolated between the last two snapshots, displayed slightly in the past (e.g. ~100ms buffer) so there's always a "next" snapshot to interpolate toward. Purely cosmetic — physics stays server-authoritative, consistent with the project's "render is cosmetic, physics is truth" convention (see "Conventions established so far" in CLAUDE.md), so it carries no security/trust implications.
  - The local player is the tricky part — interpolating *your own* avatar the same way will feel laggy/disconnected from input. The standard fix for that is full client-side prediction (simulate locally, reconcile against server snapshots), which is a meaningfully bigger lift.
  - Leaning: ship interpolation for *remote* players only first (removes most of the visible jitter with a small, low-risk change); treat local-player prediction as a separate follow-up only if "my own movement feels laggy" turns out to bother players in practice.
- [ ] **Chat history for newly-joining clients** — raised right after the chat feature shipped: today chat is purely live/ephemeral (deliberate, per the doc comment above `handleChat` — "no 'restore on restart' expectation, contrast `handleDraw`'s `storage.put`"), so anyone who joins mid-conversation sees nothing earlier than their own join, same as `snapshot`/`player_joined`. A simple version wouldn't need any new protocol message type at all:
  - Keep a small rolling in-memory log server-side (`chatLog: ChatEntry[]`, capped at the last N — maybe mirroring the client's existing `MAX_CHAT_LOG = 200`), pushed to in `handleChat` right before broadcasting
  - Fold that array into the existing `world_state` message (the same message that already carries existing players/platforms for late joiners) rather than inventing a separate `chat_history` type
  - Client-side: bulk-append those entries through the same `appendChatEntry` the live path already uses
  - The one real design fork is **persistence across restarts**: an in-memory-only buffer is simplest (zero `room.storage` writes, resets on room respawn — arguably *fine*, since chat's ephemerality is already framed as a feature, not a gap) vs. persisting via `room.storage` like platforms do, which would mean a storage write on *every chat message* — a much higher write-rate than `draw`/`erase` (which are cooldown-gated to ~1/sec and ~1/250ms respectively) since chat can fire as often as every `CHAT_COOLDOWN_MS=400`ms per player, across potentially many players.
  - Leaning: in-memory rolling buffer folded into `world_state` — simplest version, no new message type, and consistent with chat's existing "live conversation, not a permanent record" framing.
